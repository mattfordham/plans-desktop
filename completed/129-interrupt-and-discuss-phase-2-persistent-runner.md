## What
Follow-up to #128.

Phase 2 of interrupt-and-discuss. Replace the one-process-per-action runner with a persistent, streaming-input process per plan, so a held conversation is a live session rather than a chain of `--resume` launches.

Scope:
- **Persistent streaming-input runner.** `run-task.ts` keeps one `query()` open with an async-iterable prompt stream. The app feeds follow-up user messages into it instead of spawning a new `node run-task.js --resume <id>` for each turn or action.
- **Real interrupt.** Stop calls `query.interrupt()` instead of SIGTERM, so the agent halts mid-turn and the session stays live in the same process. No `tool_use` is left without a `tool_result`, and nothing has to be reloaded from the transcript.
- **Typing while working.** The dock composer stays usable while the agent is running. A message sent mid-run either queues for the next turn or interrupts and redirects. This replaces the disabled "Stop to interrupt" band.
- **`AskUserQuestion` in held sessions.** A held or discuss session can park on an `AskUserQuestion` and show the `ParkedQuestionForm`, just like action runs do today. Read-only discuss turns currently can't.

Phase 1 (#128) stays the baseline. Fire-and-forget actions keep clean context, a finished action closes its session, and Close conversation is still one click.

## Why
Phase 1 (#128) holds an interrupted session by SIGTERM-ing the runner and resuming the session id in a new process for every turn. That works, but it has costs:
- each turn pays a process spawn and a history reload;
- a Stop mid-tool can leave a dangling `tool_use`;
- the user can't type while the agent works;
- held discuss turns can't ask the user a structured question.

A persistent streaming-input process with `query.interrupt()` gives the actual Claude Code interaction model: interrupt, redirect, answer questions, all in one live session.

## How Summary
Give `run-task.ts` a `--session` mode. In that mode the SDK `query()` takes an async-iterable prompt queue, and a stdin control protocol (`user` / `interrupt` / `answer` / `close`) drives it. The app launches resumable actions and discuss turns as session processes. A clean action finish still closes its process (Phase 1 clean context). A Stop calls `query.interrupt()`, which leaves the process alive and idle as the plan's live held session. Follow-up messages and Continue go into that session over stdin, and discuss turns can park on `AskUserQuestion`. Read-only discuss turns inside a write-capable session are enforced per turn by a `PreToolUse` posture hook. Action chips launched from a live session hand off (close, then a fresh `--session --resume` process), because cwd, system prompt and allowlist are fixed when the query starts.

## Assumptions

### Initial (from elaboration)
- [low] Session lifetime: resumable actions and discuss run as session processes. A clean action finish exits (clean context), an interrupt keeps the process alive as the held live session, and fire-and-forget behaviour is otherwise unchanged. **Why:** matches the task's "a finished action closes its session" while making Stop a real `interrupt()`; research listed per-plan always-on sessions as the alternative.
- [low] Mid-run send interrupts and redirects (keeps #128 behaviour). There is no separate "queue for next turn without interrupting" gesture. **Why:** the first option; the redirect waits for the interrupted turn's end, so no stale queued message runs.
- [low] Action chips (Execute/Elaborate/Review/Complete) from a live session hand off (close, then a fresh `--session --resume`) rather than being pushed into the session. **Why:** cwd, systemPrompt and allowedTools are fixed at query start; review/complete depend on their own system prompt.
- [low] Read-only discuss turns in a write-capable session are enforced by a per-turn `PreToolUse` posture hook, not by a separate read-only process. **Why:** under `acceptEdits`, allowlisted Write/Edit never reach `canUseTool`; the spike (Step 1c) confirms the hook works.
- [low] Budget is one session-wide cap equal to the launching mode's cap (no per-turn cost-delta enforcement). **Why:** `maxBudgetUsd` is per query; per-turn caps need delta tracking, which is out of scope.
- [high] Kept reviews, capture modes and executeYolo stay fire-and-forget single-turn processes. **Why:** they never resume a hold today (`resumesHeldSession`), and kept reviews run in a worktree cwd that `nextHold` never holds.

### Discovered during execution
- [low] A `user` control line with a missing or unknown `posture` is treated as `discuss` (read-only). **Why:** the safe default; a malformed line must never unlock writes.
- [low] Discuss posture also denies `Agent` / `Task`, on top of Write/Edit/NotebookEdit/Bash. **Why:** a subagent could write on the turn's behalf; the old read-only discuss never allowlisted them either. Config `extraAllowedTools` and interactive MCP tools on the base list (e.g. Playwright click/type) are NOT blocked in a discuss turn, which is wider than the old fixed discuss allowlist.
- [low] Whether a session ends after a turn is keyed on that turn's POSTURE, not the launch mode: only a finished, non-interrupted `action` turn ends the input queue. **Why:** a discuss/apply follow-up inside an interrupted execute session must keep it open, while an `action` line (e.g. a Continue) that finishes cleanly should close it like a finished action. Step 6 should send Continue with posture `action` if it wants the held action to run to completion and exit.
- [low] `apply` posture without a task id (whole-project discuss) degrades to `discuss`. **Why:** apply is per-plan; there is no single plan file it could be scoped to.
- [low] `action` posture text is sent verbatim (no wrapper prompt); `discuss`/`apply` text is wrapped in the session follow-up prompts. **Why:** action lines are slash commands or Continue nudges that must reach the agent unchanged (trailing prose becomes skill `$ARGUMENTS`).
- [low] `close` is graceful: it denies any parked question and ends the input, but a running turn finishes before the process exits (spike: ending the input mid-turn lets the turn complete). To stop fast, send `interrupt` then `close`; SIGTERM remains the hard stop. **Why:** keeps EOF (= close) from ever cutting a turn short.
- [low] Interrupt detection: `terminal_reason` `aborted_tools` / `aborted_streaming`, or an interrupt requested during the turn that ended in a non-success result. **Why:** spike findings below; a late interrupt that loses to a successful finish is reported as a normal finish.
- [low] After the input has ended and every turn has reported `done`, the SDK's trailing "Claude Code returned an error result" throw (seen when the CLI exits after an interrupted turn) is swallowed. **Why:** the session is over and fully reported; emitting `error` then would misreport a clean close.
- [high] In session mode `session` is emitted once per process, and `turn running` is also emitted when an SDK `init` arrives while idle (a queued message started a turn). **Why:** spike: the SDK re-sends `system/init` with the same session id at the start of every turn.
- [high] Session `costUsd` on `done` is the SDK's cumulative `total_cost_usd` for the whole session, not per turn (observed in the smoke run); `turns` is per turn. **Why:** that is what the SDK reports; the Swift side should not sum `costUsd` across a session's turns.
- [low] `RunEvent.done` gains a 4th associated value `interrupted: Bool = false` rather than a new event case; the encoder writes the key only when true. **Why:** the wire event is still `done`; the default keeps every construction site source-compatible, and only the three `case let .done(...)` patterns needed a trailing `_`.
- [low] `TaskRun` tracks each session turn's posture with a FIFO seeded by the launch posture (`initialPosture(mode:apply:)`, mirroring the runner) and appended by `send`; `turn running` pops it into `turnPosture`. `send` ignores blank text so the FIFO never desyncs from the runner (which drops empty text). **Why:** `holdAfterSessionTurn` needs the ended turn's posture, and the runner doesn't echo it back.
- [low] `turnActive` is event-driven only (`turn running` / `turn idle`, cleared by `finish`); `send` does not set it optimistically. **Why:** the runner is the source of truth; a second send in the gap before `turn running` is queued by the runner as the next turn, not lost.
- [low] A session turn's start resets `reply` and `lastTurnInterrupted` (per-turn), while `sessionID`, `summary` (cumulative cost) and `error` persist across turns. `onTurnEnd` fires only on a `turn idle` that follows `turn running`, after `onEvent`, and never from `finish`. **Why:** an interrupted turn must not report the previous turn's reply as its summary; a process exit is already a finish.
- [low] `close()` writes the `close` line but leaves the stdin pipe open; `finish` closes it when the process exits. **Why:** closing the handle on the writer queue would race `finish`'s close on the main actor.
- [low] `sendDisposition` gives a live session precedence over the #128 fire-and-forget paths, and refuses while a send is already queued even if the session is idle. `hasLiveSession` should be true for a RUNNING session-mode `currentRun` as well as an adopted `liveSession`, so a mid-run send interrupts over stdin instead of SIGTERM. **Why:** one live process per plan; with no session the decision is byte-for-byte the #128 one (defaults false).
- [low] `holdAfterSessionTurn`: a turn "of the held session" is one whose id equals the hold's id OR whose process was resumed from it (fork tolerance, like `holdAfterDiscussTurn`). An interrupted discuss-launched session with no hold sets none (as `nextHold` never holds discuss), but the live session stays adopted for follow-ups. A failed (non-interrupted) action turn keeps the hold. **Why:** mirrors `nextHold`'s guards so Continue always re-launches a real action mode.
- [low] Answering a discuss-turn question returns the gate to `working(.discuss)` through the existing `syncStateFromRun(discussRun)` (the run's mode is `.discuss`). For a session launched as an action, a discuss-posture follow-up synced that way would read `working(<launch mode>)`. **Why:** no new API needed for the pure discuss case; Step 6 must choose the state for follow-up turns inside an action session.
- [low] A session run is the agent's `liveSession` from LAUNCH until its process exits, is handed off or the conversation closes. While a turn runs it also sits in the slot for that turn: `currentRun` for an action turn (gate + run log) or `thread.activeRun` for a discuss/apply turn (events folded by `applyDiscussEvent`). Between turns it is in neither (`releaseSessionTurn`). Event routing and turn ends are by slot identity, and anything from a session the agent no longer tracks is ignored. **Why:** the simplest model that keeps every `currentRun`-based check (spinners, `runs`, `isRunning(taskID:)`, Retry) reading an idle held session as not running, without touching those call sites.
- [low] Discuss/apply-posture turns of a session are NOT appended to `run.lines`, so the run log stays the action turns' log and the discussion renders once, as thread turns. Continue re-begins the session's own run segment (moved to the end of the transcript, never duplicated). **Why:** otherwise a discussion inside an execute session would render twice (log + bubbles).
- [low] Per-plan discuss turns launch as sessions; the whole-project discuss (empty task id) stays a single-turn process. **Why:** `ProjectDiscussionView`'s stop/end paths are outside this task's scope, and `apply` posture already degrades without a task id.
- [low] An idle discuss-only session stays alive until New conversation, Close conversation, any action launch on that plan, or quit, so each discussed plan can keep one idle node process. **Why:** the runner keeps a discuss session open until close/EOF, per Step 2; auto-closing idle sessions is out of scope.
- [low] Continue goes into the live session (verbatim `action` text `TaskRunner.continueText(mode:)`) only when the live session is idle and was launched in the HELD mode; otherwise it opens the action's modal, which relaunches with `--resume`. **Why:** a discuss-launched process has the discuss budget/config, and a review session can't continue an execute hold.
- [low] EVERY `run(...)` / `review(...)` launch hands off the live session (close, then the fresh launch resumes `heldResume`), including action-bar buttons, housekeeping and a kept review (which keeps the hold but not the process). **Why:** one live process per plan; a kept review left beside a live session would make a mid-review send interrupt the wrong process.
- [low] The hand-off launches `--session --resume <held id>` while the old process is still closing gracefully. **Why:** not covered by the Step 1 spike; the old process is idle (or interrupted) and only exits, so no concurrent writes to the session are expected. Observe in Step 8.
- [low] Stop, or a send that must interrupt, before a session's first turn has started (still launching) falls back to SIGTERM (`interruptOrStop`). **Why:** the runner ignores `interrupt` while idle, so the first turn would otherwise run to completion.
- [low] `sendDisposition`'s `sessionTurnActive` is `turnActive || agent busy`, and `hasLiveSession` is true only when the live session is what the agent is busy with (or the agent is idle). **Why:** it covers the gap between a `send` and its `turn running`, and a busy non-session run (kept review) keeps the #128 stop-then-launch path.
- [low] Store reload: an INTERRUPTED action turn reloads from `onTurnEnd`; a finished action turn reloads once, from the process-exit finish that follows it (not twice). **Why:** the runner always exits after a non-interrupted action turn, and the finish path already reloads and syncs.
- [low] A session process that exits on its own takes its hold from `holdAfterSessionTurn` (so a Continue inside the session that finishes cleanly clears the hold even though the process wasn't launched with `--resume` of it). A SIGTERM stop, an abandoned question or a session with no id still uses `nextHold`. **Why:** `nextHold` only clears a hold for a run resumed FROM it.
- [low] A session turn start also resets `error`, `summary` and `lastStopReason`, so the run segment's summary/error rows reflect the latest turn. **Why:** `SessionTurnEnd.failed` must be per turn.
- [low] An interrupted discuss turn reads "Cancelled" (`DiscussionThread.markLastTurnInterrupted`, which also applies after `done` cleared `isPending`). A parked discuss turn's activity reads "Waiting for your answer…". **Why:** matches the #128 cancelled-turn look; the form itself lives in the dock footer.
- [low] New conversation closes a live session unless it is the held one; Close conversation always closes it. **Why:** New conversation keeps the hold (#128), and the next turn would resume that session anyway.
- [low] Quit replies `.terminateLater`. `stopAllRunning` sends `interrupt` + `close` to every live session, polls every 50 ms, SIGTERMs survivors after 2 s, then replies. Idle held sessions don't trigger the "running tasks" prompt, but are still closed (quit can wait up to the grace period). **Why:** AppKit can't wait inside `.terminateNow`, and EOF alone would let a running turn finish.
- [low] A discuss turn inside an action-launched session reads as `working(.discuss)` in the gate and as "Discussing" in the toolbar snapshot (`PlanAgent.isDiscussionTurn`). **Why:** segment 2 left this state open; the launch mode would mislabel it.

## Changes
### Spike findings (SDK 0.3.215)
Scratch scripts (not committed) ran against the installed SDK with `claude-haiku-4-5`, `permissionMode: "acceptEdits"`, in a temp project with a trivial `.claude/commands/greet.md` and `.claude/skills/hello/SKILL.md`.

- **(a) Slash command as the first streaming-input message: works.** `/greet ARG1` and `/hello ARG1` produced the same output (`ZEBRA-QUOKKA-42 ARG1`, `PLATYPUS-77 ARG1`) whether sent as a string prompt or as the first `SDKUserMessage` (`{type:"user", message:{role:"user",content:text}, parent_tool_use_id:null, origin:{kind:"human"}}`) of an async iterable. Init `capabilities` = `["interrupt_receipt_v1","msg_lifecycle_v1"]`.
- **(b) `query.interrupt()` mid-tool: known shape, no dangling tool_use, session continues.** While a `Bash` `sleep 20` ran, `interrupt()` resolved immediately with `{"still_queued":[]}`. The stream then delivered: a `user` message with a `tool_result` for the pending tool_use (`is_error:true`, "The user doesn't want to proceed with this tool use. The tool use was rejected…"), a `user` text message `[Request interrupted by user for tool use]`, then `result` with `subtype:"error_during_execution"`, `terminal_reason:"aborted_tools"`, `stop_reason:"tool_use"`, `is_error:true`, `result:""`, `errors:["[ede_diagnostic] …"]`. Interrupting mid-text instead gives `terminal_reason:"aborted_streaming"`, `stop_reason:null`, text `[Request interrupted by user]`. A message pushed afterwards ran in the SAME session (same `session_id`), and the agent coherently said the sleep was rejected and did not finish. Every turn starts with a fresh `system/init` carrying the same session id. No `session_state_changed` messages were seen.
  - Interrupting while `canUseTool` parks `AskUserQuestion`: the callback's `signal` aborts, and the result is again `aborted_tools`.
  - Gotcha: if the input stream ENDS right after an interrupted (error) result, the SDK throws `Claude Code returned an error result: [ede_diagnostic] …` from the iterator as the CLI exits. The runner swallows it once the session is closed and fully reported.
  - Ending the input stream mid-turn does NOT abort the turn: it runs to completion, then the stream ends.
- **(c) PreToolUse hook deny under `acceptEdits`: works.** With Write/Edit/Bash in `allowedTools`, a hook returning `{hookSpecificOutput:{hookEventName:"PreToolUse", permissionDecision:"deny", permissionDecisionReason}}` blocked all three (Edit verified on an existing file); the reason arrives as an `is_error` tool_result, and no file was written.

### Runner session protocol (Steps 2-3)
`run-task.ts --session` (see its NDJSON header): stdin control lines `user{text,posture}` / `interrupt` / `answer{toolUseId,answers}` / `close` (EOF = close); stdout adds `turn{state:"running"|"idle"}` and `done.interrupted:true`. Posture hook (`toolAllowedForPosture`), session discuss prompts that permit AskUserQuestion, session allowlist = base + extras minus AskUserQuestion, budget = launching mode's cap. An end-to-end haiku smoke run confirmed: interrupt mid-Bash → `done.interrupted` and the process stays idle; a follow-up answers in the same session; a parked `question` answered over stdin continues the turn; interrupting a parked question then `close` exits 0 with no `error`; a clean `action` turn exits the process by itself.

### Swift session model (Steps 4-5)
`TaskRun` gains `session` (argv `--session` before `--resume`; stdin pipe for any session), `SessionPosture`, pure `userLine` / `interruptLine` / `closeLine` / `initialPosture`, the writers `send(text:posture:)` / `interrupt()` / `close()` on the answer queue, and per-turn state (`turnActive`, `lastTurnInterrupted`, `turnPosture`, `onTurnEnd`). `RunEvent` decodes `turn{state}` and `done.interrupted`. A `turn idle` clears `pendingQuestion` and fires `onTurnEnd` with the process alive; a process exit still goes through `finish`. `PlanAgent` gains `liveSession` with `adoptLiveSession` / `dropLiveSession`, `pendingQuestionRun`, the session-aware `sendDisposition` (`.deliverToSession`, `.interruptSessionThenDeliver`), a pure `holdAfterSessionTurn` with a `SessionTurnEnd` snapshot, and `endSessionTurn` (hold, lineage, idle). Discuss `.question` now parks the gate in `needsInput`. Nothing is wired into `TaskRunner`'s launch/stop/send yet: the new dispositions return `false` in `TaskRunner.send` until Step 6.

### Live-session wiring, dock and docs (Steps 6-7)
`TaskRunner` launches resumable actions (not a kept review, capture modes or executeYolo) and per-plan discuss turns as `--session` runs, wired by `wireSession`: the run is the agent's `liveSession` from launch; while a turn runs it sits in `currentRun` (action) or `thread.activeRun` (discuss/apply). `stopAgent` interrupts a session turn (SIGTERM only for non-session runs or a still-launching session). On an interrupted turn end the agent holds the session (`endSessionTurn`), releases the run (`releaseSessionTurn`), reloads the store and delivers any queued send. `send` / `ask` deliver into an idle live session as `user` lines (`discuss` / `apply`); a mid-turn send queues and interrupts. `continueHeld` sends `continueText` as an `action` turn. `run` / `review` hand off (close, then a fresh session resuming `heldResume`). `closeConversation` and `resetDiscussion` close the process. `stopAllRunning(gracePeriod:completion:)` does interrupt + close, then SIGTERM. `liveRuns` counts a live session only while `turnActive`, and `hasLiveSessions` drives the quit path. `PlanAgent` gains `isDiscussionTurn`, `releaseSessionTurn`, `endSessionDiscussTurn`, session-aware `beginRunSegment` pruning, `syncStateFromRun` and `completeRunSegment` hold. `DiscussionThread` gains `markLastTurnInterrupted` and a waiting-for-answer activity. `AgentDock`'s question footer resolves `pendingQuestionRun` and answers through `TaskRunner.answer`; Stop goes through `stopAgent`, Continue tries `continueHeld` first, and the tooltips are a pure `buttonHelp(_:hasLiveSession:)`. The active-runs answer sheet uses `questionRun(forKey:)` / `stopAgent(key:)`. `PlansApp`'s quit replies `.terminateLater`. CLAUDE.md and the `RunEvent` contract comment describe Phase 2. Fire-and-forget tests that used plan discuss for the SIGTERM/cancel paths now use the whole-project discuss.
