# Elaborate Button: Use Dialog With Input and "Deep" Option

## What
The "elaborate" button for pending plans in the tables simply begin the elaboration process. Update to use dialog with input for additional elaboration message AND "Deep" option.

## Why
Today the table's Elaborate glyph is a one-click, fire-and-forget `runner.run(... mode: .elaborate)` — the user cannot steer the elaboration or request the deeper reasoning pass, even though plans-cc already supports both an `--deep` flag and free-text guidance. This adds a small dialog (mirroring the existing Refine sheet) so a pending plan can be elaborated with optional guidance text and an optional Deep toggle, giving parity with the Refine (`.reElaborate`) and New-Plan capture flows that already expose these controls.

## How Summary
Add a new `ElaborateModal` sheet — a near-verbatim copy of `ReElaborateModal` with the text input made *optional* and a "Deep" checkbox lifted from `NewPlanModal` — and present it from the pending-plan Elaborate glyph in `ProjectCard` (and the sibling header button in `PlanDetailView`) via the existing `.sheet(item:)` request-struct pattern, replacing the current direct `runner.run(...)` call. Thread the two new inputs end-to-end through the already-present `deep` plumbing (add a `deep:` parameter to `TaskRunner.run`) and by giving the `.elaborate` mode an *optional* `--description` channel: flip `RunMode.elaborate.usesDescription` to true, relax `run-task.ts` validation so `elaborate` accepts (but does not require) a description, and fold the guidance into `buildElaboratePrompt` the way `buildReElaboratePrompt` already does. Deep is reused orthogonally — no new `RunMode`.

## Assumptions

### Initial (from elaboration)
- [low] Forward the "additional elaboration message" by giving the `.elaborate` mode an OPTIONAL `--description` channel (Open Question option a), rather than routing an elaborate-with-guidance through `.reElaborate`. **Why:** research showed `.reElaborate` is plan-elaborate's Path C for an already-*elaborated* task and leaves status `elaborated`; using it on a `pending` task is semantically wrong. Option (a) matches the existing `buildReElaboratePrompt` guidance-block convention, but it touches both Swift and TS and the initial-elaboration skill's honoring of free-text guidance is unconfirmed (see below), so flagged low.
- [low] Make the guidance text input OPTIONAL — do NOT gate submit on non-empty text. **Why:** the current one-click Elaborate has no input at all; requiring text would regress "just elaborate". Refine requires text because guidance is its whole purpose, but an elaborate-with-message is an optional enhancement. UX decision not specified in the source description.
- [high] Reuse the existing orthogonal `deep` flag rather than inventing a new `RunMode`. **Why:** `TaskRunner.swift` docs and `run-task.ts` are emphatic that Deep is orthogonal to mode; the `--deep` → trailing ` deep` token path is already wired end-to-end for `.elaborate` (only `TaskRunner.run` lacked the parameter). Only one plausible approach surfaced.
- [high] Model the new modal on `ReElaborateModal` (single-purpose fixed-task sheet, no draft persistence, `PlanTextEditor`, ⌘↩ submit) rather than `NewPlanModal`. **Why:** `ReElaborateModal` is the direct structural match (fixed task + project, one editor, hands off to `runner.run`); research explicitly flagged it as the near-perfect template and warned against adding draft persistence.
- [low] Default the Deep toggle OFF and add no placeholder/default guidance beyond an "optional" hint. **Why:** `NewPlanModal` defaults Deep off; there is no source-description guidance on the default, so mirror the established capture-modal default.
- [low] Apply the dialog to BOTH the table-row glyph (`ProjectCard`) AND the detail-window header button (`PlanDetailView`), not only the table. **Why:** the description says "in the tables", but leaving the sibling detail button as bare fire-and-forget while the table gets a dialog would be inconsistent; research recommended both. Scope decision the description did not settle.
- [low] Confirm the plans-cc `plan-elaborate` skill honors free-text guidance on an INITIAL (Path A/B) elaboration, not just Path C. **Why:** the prompt builder can always inject a guidance block, but the skill's initial-elaboration paths were not verified to consume it; if they don't, the guidance would be delivered but ignored. Verify during execution (Step 4/9) and record as a discovered assumption if the behavior differs.

### Discovered during execution
- [high] Flipped `RunMode.elaborate.usesDescription` to `true` as the plan specified, after confirming `usesDescription` is consulted ONLY by `TaskRun.spawn` (guarded by `let description, !description.isEmpty`) and by pure-flag test assertions — never to validate/require a description or gate a submit button. **Why:** No `requiresDescription` distinction was needed; `spawn` already omits the flag when the description is nil/empty, so `.elaborate`'s description stays genuinely optional.
- [high] Updated the existing `testRunModeUsesDescriptionFlag` assertion (`XCTAssertFalse(RunMode.elaborate.usesDescription)` -> `XCTAssertTrue`) plus the stale "reElaborate is the ONE mode where both flags are true" doc comments in `TaskRunner.swift` / `TaskRunnerTests.swift`. **Why:** Step 2 intentionally inverts that behavior, so the pre-existing assertion would otherwise fail; the doc comments describe an invariant the change deliberately relaxes.
- [low] `buildElaboratePrompt` trims the description and treats whitespace-only guidance as absent (emitting today's prompt unchanged), and takes `description` as a trailing optional third parameter after `deep`. **Why:** A blank/whitespace input from the dialog should not inject an empty `"""` block; a trailing optional keeps all existing call shapes valid. The alternative (matching `buildReElaboratePrompt`'s required-positional `description` before `deep`) would have forced every caller to pass a value.
- [low] The guidance block in `buildElaboratePrompt` mirrors `buildReElaboratePrompt`'s `"""`-delimited format but is worded for a first elaboration ("guidance for this elaboration") rather than a Path-C refinement, and no extra numbered Requirement was added referencing it. **Why:** The existing three requirements already cover autonomy/research/end-state; adding a fourth would diverge the two builders' requirement lists without changing behavior.
- [low] `parseArgs` returns `description` for `elaborate` via a dedicated branch placed after the shared `if (!taskId) return null` guard, rather than widening the `reElaborate` branch. **Why:** Keeps `reElaborate`'s both-required validation intact while making `elaborate` the only mode with an optional description, and keeps execute/delete's arg shape byte-identical.
- [low] Placeholder wording is "Add optional guidance for elaborating plan #NNN…" — explicitly carrying the word "optional". **Why:** `ReElaborateModal`'s "Add guidance to refine plan #NNN…" reads as a required field, and this sheet's whole point is that an empty box is a first-class submit; the word "optional" is the cheapest way to signal that without adding a second line of chrome. Exact wording was not specified.
- [low] Placed the always-enabled Deep toggle in its own `HStack(spacing: 16)` between the editor and the `Divider()`, matching `NewPlanModal`'s toggle row (leading-aligned, trailing `Spacer()`) rather than inlining it into the Cancel/Elaborate button row. **Why:** it reads as an input to the action, not a button; reusing `NewPlanModal`'s toggle-row geometry keeps the two capture sheets visually consistent. Placement was not specified.
- [high] Omitted `NewPlanModal`'s `.disabled(!elaborate)` from the Deep toggle and kept its help text verbatim. **Why:** the segment prompt is explicit, and the gate exists in `NewPlanModal` only because Deep modifies an elaboration pass that may not run there — in this sheet the elaboration always runs.
- [high] `submit()` maps a whitespace-only box to `nil` (not `""`) before calling `runner.run`. **Why:** segment 1 made `TaskRun.spawn` emit `--description` only for a non-nil, non-empty value, so `nil` reproduces today's bare elaborate exactly; `""` would rely on the same guard but muddies intent at the call site.
- [low] Declared a distinct `ElaborateRequest` struct in `ProjectCard.swift` rather than reusing `ReElaborateRequest` for both sheets. **Why:** the two `.sheet(item:)` presentations must be independently keyed, and a shared type would invite accidentally driving one sheet from the other's state; the cost is ~6 duplicated lines. A single shared `PlanSheetRequest` type was the plausible alternative.
- [high] Added a per-glyph `elaborateRequest` state + second `.sheet(item:)` on the card (rather than a bool) and a plain `showElaborate` bool on `PlanDetailView`. **Why:** exact pattern-match with the existing `reElaborateRequest`/`showReElaborate` pair — the card renders many rows so the sheet must carry the target row, while the detail view is already scoped to one task.
- [high] Left the detail header's Elaborate `Button` without added logging. **Why:** it had none before (unlike the card glyph's `cardLog.notice`), and its sibling Refine/Execute header buttons are likewise unlogged; the new `ElaborateModal` logs the submit itself.
- [high] Did NOT add any TypeScript test for the `run-task.ts` changes; the TS side is covered instead by the project's existing strict `tsc --noEmit` typecheck plus the Swift-side arg-shape assertions (`RunMode.elaborate.usesTaskID`/`usesDescription`, and the raw-value round-trip that pins the `"elaborate"` literal both sides switch on). **Why:** `Tools/work-task/` has NO test infrastructure whatsoever (only a `build` script, no runner, no test files), and CLAUDE.md mandates no external dependencies — introducing vitest/jest/node:test purely for this task would be a structural change well beyond its scope. The residual gap is real and worth flagging at review: `buildElaboratePrompt`'s guidance-block *formatting* and `parseArgs`'s new `elaborate` branch are verified only by typecheck and inspection, so a logic regression there (e.g. the guidance block emitted in the wrong position) would not be caught by any automated test.
- [low] Pinned the `.elaborate` contract with three run-level tests asserting STORED PROPERTIES (`description`, `deep`) rather than the spawned process's argv. **Why:** follows the file's established and heavily documented precedent (`testDeepRunCarriesDeepFlag`, `testCaptureRunCarriesDescriptionAndSyntheticIdentity`) — asserting argv would require spawning a real `node` process, which the whole test file deliberately avoids for purity/flakiness reasons. Consequence: the `spawn` binding that actually omits `--description` for a nil/empty value is verified by inspection, not execution.
- [low] Added `testElaborateDeepAndDescriptionAreIndependent` beyond the two tests the step required, covering deep-without-guidance and guidance-without-deep. **Why:** the dialog exposes two independent controls, and the step's both-set and neither-set cases alone would still pass if the two were accidentally coupled (e.g. deep implying a description); the mixed cases close that hole.
