# Bug: headless capture/elaborate runs can't use Sentry MCP tools (or any other tool not on the allowlist)

**ID:** 092
**Created:** 2026-10-23T14:19
**Type:** bug
**Status:** completed
**Branch:** fix/092-headless-capture-cant-use-mcp-tools
**Completed:** 2026-10-29T09:32

## What
When the plans desktop app captures and elaborates a task, it launches a Claude Code session through the Agent SDK. In that session, every Sentry MCP call is refused. On 2026-10-23, task #1120 in the Client A repo (~/Work/client-a) was elaborated without the Sentry issue it was created for. The tools loaded fine, but each call failed:

```
mcp__sentry__get_sentry_resource → is_error: "Claude requested permissions to use mcp__sentry__get_sentry_resource, but you haven't granted it yet."
mcp__sentry__search_issues      → same error
```

Evidence: the session transcript is `~/.claude/projects/-Users-<user>-Work-client-a/<session-id>.jsonl`. Its metadata is `entrypoint: "sdk-ts"`, `permissionMode: "acceptEdits"`, `version: 2.1.215`. The failed calls are at about 20:38:40Z and 20:38:47Z.

Root cause:
1. The app runs the session with `permissionMode: "acceptEdits"`, which only auto-approves file edits. Any other tool that isn't on the allowlist needs an approval prompt. The SDK session has no `canUseTool` callback or UI to answer that prompt, so the call is refused and the agent can only continue without it.
2. The user's existing Sentry allow rules use old tool names: `mcp__sentry__get_issue_details`, `get_trace_details`, `search_events` (in `.claude/settings.local.json`). The current Sentry MCP server's tools (`get_sentry_resource`, `search_issues`, `search_errors`, `analyze_issue_with_seer`, etc.) don't match those rules. That gap makes the problem visible here, but any MCP tool not on the allowlist would fail the same way.

What to change in the app (pick what fits its design):
- Add a `canUseTool` callback that sends permission requests to the desktop UI so the user can approve or deny them, the way the CLI does. At minimum, record denials so they show up in the run.
- Or pass an explicit `allowedTools` list in the SDK `query()` options for elaborate/capture runs. It should include read-only MCP tools the plan workflows rely on, e.g. `mcp__sentry__get_sentry_resource`, `mcp__sentry__search_issues`, `mcp__sentry__search_errors`, `mcp__sentry__search_events`, `mcp__sentry__search_traces`, `mcp__sentry__search_logs`, `mcp__sentry__analyze_issue_with_seer`, `mcp__sentry__find_organizations`, `mcp__sentry__find_projects`. Leave out write tools such as `mcp__sentry__update_issue` so unattended runs can't change issues. A user-configurable allowlist in the app's settings would be better than hardcoding one.
- Check `settingSources`. If the user's project and local `settings.json` allow rules should apply, make sure the SDK call loads `['user', 'project', 'local']`.
- Show permission denials in the UI. Today the elaboration finished as "elaborated" and only said in its own text that Sentry was unavailable. If a run hits permission denials, mark it so the user can see the plan was built on incomplete information, e.g. with a warning badge or an "N tool calls denied" note.

How to verify: in the Client A repo, capture and elaborate a task from a Sentry issue URL through the app, e.g. https://<org>.sentry.io/issues/<issue-id>/. Confirm in the new session's transcript that `mcp__sentry__get_sentry_resource` returns issue data instead of the "haven't granted it yet" error, and that the elaborated plan names the actual error class and its file:line.

## Why
When a hand-off run elaborates a task built around a Sentry (or any other non-allowlisted MCP) issue, the agent is silently denied the one tool it needs and produces a plan built on incomplete information — which still reports as a clean "elaborated" success. Fixing this restores the app's core value for issue-driven tasks (the plan names the real error class and file:line) and makes it honest about degraded runs instead of masking them.

## How Summary
The entire defect lives in `Tools/work-task/run-task.ts`, where `query()` is called with `permissionMode: "acceptEdits"` and an explicit closed `allowedTools` list that omits every `mcp__sentry__*` tool. Because `allowedTools` is an explicit allowlist, any tool not on it needs an interactive approval that this headless session has no way to answer (no `canUseTool` callback), so the call is denied. The fix extends that allowlist with the read-only Sentry tools the plan workflows actually use (write tools like `update_issue` deliberately excluded), optionally driven by a user-configurable allowlist, and surfaces any permission denials that still occur on the NDJSON → Swift path so a degraded run is visibly flagged rather than reported as a clean success.

**Files of note:**
- `Tools/work-task/run-task.ts` — the SDK launcher; holds the `query()` options with `permissionMode`, the explicit `allowedTools` array (lines ~819-856), and the NDJSON `emit()` contract. Primary fix site.
- `Sources/Plans/TaskRunner.swift` — Swift NDJSON consumer; `RunEvent` enum (activity/text/done/error) and `TaskRun` accumulation. A denial signal must be decoded and counted here.
- `Sources/Plans/RunOutcomeLog.swift` — persists a run's terminal outcome (`stopReason`, failure text); the place a per-run "N tool calls denied" note would live.
- `Sources/Plans/PlanDetailView.swift` — renders run failure/outcome text to the user; where a denial badge/note would appear.
- `~/.claude/settings.local.json` and `<project>/.claude/settings.local.json` — the user's Sentry allow rules, which use stale tool names and therefore don't help (context, not a file to edit).

## Assumptions

### Initial (from elaboration)

The `canUseTool` → desktop-UI prompt remedy was deliberately NOT adopted (see below).
- [high] Chose extending `allowedTools` over adding a `canUseTool` callback as the primary fix. **Why:** These runs are unattended (no interactive UI by design — the whole file's prompt builders say "Do NOT ask the user any questions"), so a `canUseTool` prompt would have nothing to answer it and would just re-deny. The codebase already solved the identical des-build/Figma denial with an allowlist extension, so this matches established convention. `canUseTool` is still used narrowly in Step 4 only to *detect/record* denials, not to prompt.
- [low] Settng `settingSources` was NOT added to the fix. **Why:** SDK `@anthropic-ai/claude-agent-sdk@0.3.215` loads user/project/local settings by default when `settingSources` is omitted (confirmed in `sdk.d.ts:1873-1883`), and the transcript shows even correctly-named global allow-rules still failed — so the explicit `allowedTools` whitelist, not missing setting sources, is the gate. Adding `settingSources` would be redundant and the user's stale rule names would still not match.
- [low] The user-configurable allowlist is read from the app's existing settings mechanism and only *extends* the built-in read-only base list; write tools stay excluded by default. **Why:** The description preferred "user-configurable over hardcoding" but the exact settings surface wasn't specified; extending (never shrinking) the safe base list preserves the "unattended runs can't change issues" guarantee regardless of user config. - [low] Denials are surfaced via a NEW `denied` NDJSON line + a new `RunEvent` case, rather than reusing the existing `error`/`stopReason` channel. **Why:** A denied tool call is not a terminal run failure (the run still finishes as "elaborated"), so overloading `error` would mislabel the outcome; a dedicated signal lets the UI show a non-fatal "N denied" note while the run still reports success.
