# Plans app is often using lots of Energy — diagnose and lower it

## What
Plans app is often using lots of "Energy". Any thoughts on why? Sign of underlying problem? How can we lower?

![pasted image](file://~/Library/Application Support/Plans/attachments/0F9C4665-2658-4816-B6A2-C3D797B9139D.png)

## Why
Improves efficiency and battery life by eliminating sustained background CPU/process churn: a menu-bar app that idles all day should be near-zero energy, but Plans currently re-does its full workload (git subprocess spawns + full re-parse of every task file for every project) every 5 seconds, forever — even when nothing is visible and nothing has changed. It is a sign of an underlying design gap (no change detection, no caching), not a one-off glitch.

## How Summary
Keep the 5s poll cadence (prior tasks #036/#052/#059 warn against widening it) but make each tick cheap when nothing changed: cache/throttle the git second pass so subprocesses aren't spawned every tick, mtime-gate task parsing so unchanged projects are skipped, and equality-gate store publishes so SwiftUI (including the `ImageRenderer` menu-bar label re-bake) stops re-rendering on identical data. Confirm the git-spawn hypothesis first, then fix, preserving the #051 reconciliation (`onDidReload`) ordering.

**Files of note:**
- `Sources/Plans/PlansStore.swift` — poll timer (`startPolling`, :618), `performReload` (:461), `startGitSecondPass` (:557), `applyReloadResult` publish (:545); the energy epicenter
- `Sources/Plans/GitHelper.swift` — spawns `/usr/bin/git` + `waitUntilExit()` per query (:41, :76), explicitly uncached; add caching/throttling here
- `Sources/Plans/TaskParser.swift` — `parseProject` (:253) full dir listing + read/parse of every task file per tick; add mtime gating
- `Sources/Plans/MenuBarLabel.swift` — re-bakes `ImageRenderer` bitmap on every store publish; benefits from equality-gated publishes
- `Tests/PlansTests/PlansStoreTests.swift`, `GitHelperTests.swift`, `TaskParserTests.swift` — TDD homes for the new gating/caching behavior

## Diagnosis

**Most likely:** the unconditional 5s poll spawns 2 git subprocesses per registered project on every tick with no caching — process creation/teardown dominates the Energy pane (`Sources/Plans/GitHelper.swift:31-52,66-88`, `Sources/Plans/PlansStore.swift:557-570,618-623`)
**Evidence:** `startGitSecondPass()` fires on every reload (PlansStore.swift:438, :546) and loops all projects; `GitHelper` runs `Process()` + `waitUntilExit()` per query and is explicitly uncached by design; the timer is never gated on visibility/idle (`stopPolling()` is only called from `startPolling()`), so with N projects that is 2N process spawns every 5s, ~17,280 ticks/day
**Confidence:** high

**Alternative:** full re-read + markdown re-parse of every task file for every project each tick with no mtime/change detection (`Sources/Plans/TaskParser.swift:253-334`, `PlansStore.swift:461-478`) — **Confidence:** medium (it definitely runs every tick; whether it rivals the git spawns for energy is unconfirmed)
**Alternative:** unconditional `projects = freshProjects` publish every tick even when nothing changed, invalidating all observers and re-baking the `ImageRenderer` menu-bar bitmap (`PlansStore.swift:545,593`, `Sources/Plans/MenuBarLabel.swift:44-79`) — **Confidence:** medium
**Alternative:** poll never pauses while the app is idle/invisible — a multiplier on all of the above rather than an independent cause (`PlansApp.swift:40`, `PlansStore.swift:628`) — **Confidence:** high (as multiplier)

**To confirm:** temporarily no-op `startGitSecondPass()` (or watch `sudo fs_usage -f exec` for `git` exec events), run the app idle, and observe Activity Monitor's Energy pane — if energy collapses, the git spawns dominate; if it stays high, the parse/publish path dominates

## Assumptions

### Initial (from elaboration)
- [high] Fix the per-tick work volume (git caching, mtime-gated parsing, equality-gated publishes) rather than lengthening the 5s poll interval. **Why:** research and prior tasks #036/#052/#059 explicitly warn that widening the cadence papers over the problem and degrades freshness; the cadence is intentionally synchronized across subsystems.
- [high] Git subprocess spawning (2 per project every 5s, uncached by design) is treated as the primary energy driver, with Step 1 confirming before the fix. **Why:** process spawn + `waitUntilExit` every tick is the costliest per-tick operation and Energy-pane-visible; evidence at GitHelper.swift:31-88 and PlansStore.swift:557-570.
- [low] Assumed the high Energy reading occurs while the app idles in the menu bar (per the attached Activity Monitor screenshot), not only with the browser window open. **Why:** the attachment could not be inspected from this session; the polling design makes idle-time cost the dominant scenario either way.
- [low] Visibility-gated polling (pausing via the existing `stopPolling()` when nothing is visible) is deferred as a follow-up rather than included in this task's steps. **Why:** research flagged an unresolved question about when the usage is observed, and pausing polls risks disturbing the #051 reconciliation ordering; the caching/gating steps should remove most of the cost without that risk.
- [low] Git branch/dirty freshness may lag up to ~30–60s under the throttled cadence chosen in Step 2. **Why:** an unprompted UX/scope trade-off — branch/dirty state changes far less often than task files, and this is the cheapest way to cut 2N spawns per tick.

### Discovered during execution
- [high] Implemented the Step 1 kill switch as an env-var-gated early return at the top of `startGitSecondPass()` rather than commenting the call sites out. **Why:** the step explicitly asked for a runtime switch that needs no recompile, so a single release build can be A/B'd by relaunching with a different environment; commenting out would require two builds and risk the two runs differing in more than the git pass.
- [low] Read both env vars once into file-private `let` globals instead of re-reading `ProcessInfo` per tick. **Why:** keeps the instrumentation cheap on the hot poll path; the cost is that flipping a flag requires an app relaunch, which is already the observation protocol. Alternative (per-tick read) was rejected as pointless overhead in a diagnostic meant to measure overhead.
- [low] Emit the per-tick diagnostic line from `startGitSecondPass()` (pairing parse count + spawn count) rather than from the two reload paths. **Why:** `startGitSecondPass()` is the single choke point reached exactly once per tick on both the sync and async reload paths, so one line per tick is guaranteed without duplicating logging in `reload()` and `applyReloadResult`. Required carrying the parse count in `diagProjectsParsedThisTick` between the two calls.
- [low] Counted git subprocesses analytically as `projects.count * 2` at dispatch time instead of incrementing a real counter inside the background loop. **Why:** the loop unconditionally runs exactly two `GitHelper` calls per path, so the arithmetic is exact, and it avoids adding cross-thread counter synchronization to a pass whose threading the step forbade changing. Note this reports spawns *scheduled* for the tick, not spawns *completed*.
- [high] Added no unit test for this step. **Why:** the change is purely a temporary diagnostic with both flags defaulting off (no production behavior change), and Step 5 deletes it; a test asserting an env-var read would be deleted alongside it. Existing `PlansStoreTests` (38 tests) were run to prove no regression.
- [high] `diagRecordParse` is called AFTER the `projects` assignment and BEFORE `startGitSecondPass()`/`onDidReload?()` on both reload paths. **Why:** #051 reconciliation ordering and the #059 generation guard were explicitly out of scope; inserting only between the assignment and the git pass leaves both invariants byte-for-byte intact.
- [high] Step 3 change-detection signature = per-`.md`-file `(relativePath, contentModificationDate, fileSize)` across BOTH `.plans/pending/` and `.plans/completed/`, compared element-wise as an `Equatable` `ProjectSignature`. **Why:** the step explicitly warned that a *directory* mtime does not change when an existing file's contents are rewritten in place, which would silently stop surfacing task edits. Per-file mtime+size catches in-place edits; the path set catches adds/removes/renames and the `pending/`→`completed/` move that `plan-complete` performs. Cost is one batched `contentsOfDirectory` per subdirectory with `.contentModificationDateKey`/`.fileSizeKey` prefetched, so attribute values ride along with the enumeration rather than costing a separate `stat` per file.
- [low] Deliberately did NOT include the containing directories' own mtimes in the signature. **Why:** they are strictly redundant with the per-file entry set (any entry add/remove/rename already changes the entry list) and would add a failure mode of their own without covering anything extra. Alternative considered and rejected: directory-mtime-only gating — cheaper, but silently misses in-place content edits, which is the worse bug.
- [low] Rejected content hashing (e.g. hashing each file's bytes) as the signature. **Why:** it would require reading every file every tick, which is the bulk of the cost the change gate exists to remove. Documented failure mode of the chosen signature: a same-size rewrite landing within the filesystem's mtime resolution of the prior write is missed for one tick. On APFS mtime is nanosecond-resolution so this needs two writes in the same nanosecond — unreachable in practice, and it self-heals because the next genuine change re-parses the whole project.
- [low] The cache-hit condition also requires the registry `lastSeen` to be unchanged, not just the signature. **Why:** `lastSeen` comes from `projects.json`, not from `.plans/`, so the filesystem signature cannot observe it; without this check a project whose `lastSeen` advanced would serve a `ProjectTasks` carrying a stale `lastSeen`, corrupting the browser's recency sort. Cheap (a string compare on an already-read value).
- [high] Threaded the cache through `performReload` as an in-parameter and returned a new `ReloadResult` (projects + rebuilt cache + parsed paths) rather than mutating `self`. **Why:** `performReload` is documented as pure and thread-agnostic precisely so the #059 async poll can run it off-main; making it read/write `self.parseCache` would have introduced an off-main mutation of store state. The async path snapshots the cache on main (same pattern as the existing `priorGitInfo` snapshot) and installs the rebuilt cache back on main inside `applyReloadResult`, under the SAME #059 generation guard as `projects`, so a dropped stale result leaves the cache untouched and the two can never drift apart.
- [high] The cache is rebuilt from the registry on every reload rather than mutated in place. **Why:** a project that drops out of the registry has its entry dropped with it, so it cannot resurrect a stale parse result if re-added later. Covered by `testProjectRemovedFromRegistryDoesNotLeakCachedResult`.
- [low] Added a `lastReloadParsedPathsForTesting` seam exposing which project paths were actually re-parsed. **Why:** the step required proving an unchanged project is NOT re-parsed, which is unobservable from `projects` alone (a correct cache hit and a correct re-parse produce identical output). Alternative considered: a counting `FileManager` subclass injected into `TaskParser` — rejected as more machinery for the same assertion, and it would not have distinguished signature listings from task-file reads.
- [high] `onDidReload?()` and the git second pass still fire unconditionally on every reload, outside the gate. **Why:** #051 requires the reconciliation to run on every poll tick even when all parsing is skipped, or a capture spinner orphans. Covered by `testOnDidReloadFiresEvenWhenAllParsingIsSkipped`.
- [high] Step 4 hand-wrote `Task.==` instead of relying on synthesized `Equatable`. **Why:** `Task.howProgress` is a TUPLE `(done: Int, total: Int)`, and tuples cannot conform to protocols, so Swift refuses to synthesize the conformance. The hand-written `==` compares ALL TWELVE stored properties in declaration order: `id`, `title`, `type`, `status`, `created`, `branch`, `isKeptWorktree`, `blockedBy`, `sections`, `howProgress` (both `.done` and `.total` compared element-wise), `isBlocked`, `isCompletedDir`. Nothing is omitted. A doc comment on the operator states that any property later added to `Task` MUST be added to `==` too, because an omitted field would silently drop a real on-disk change from both surfaces — far worse than the energy cost this change exists to fix. Alternative considered and rejected: changing `howProgress` to a small `Equatable` struct to unlock synthesis — it would have touched ~8 call sites across sources and tests (including `ProjectCard`, `BrowserWindow`, `TaskRunnerTests`) for no behavioral gain, expanding the diff well beyond the step's impact scope.
- [low] `ProjectTasks`, `TaskSection` and `ProjectSignature` use SYNTHESIZED `Equatable`; `TaskStatus`/`TaskType` gained an explicit (redundant, already implied by `RawRepresentable`) `Equatable` in their conformance list for documentation value. **Why:** synthesis is inherently exhaustive over stored properties and cannot drift out of sync when a field is added, so it is strictly safer than hand-writing. `ProjectTasks`'s only non-trivial members are `[Task]`, `[TaskStatus: Int]` and `Optional`s, all of which are `Equatable` once `Task` is.
- [high] Routed ALL THREE `projects` write sites (`reload()`, `applyReloadResult`, `applyGitInfo`) through one private `publishProjects(_:)` gate that assigns only when `newValue != projects`. **Why:** `@Observable` publishes a mutation on ANY assignment, even one whose value compares equal, so the gate must be a genuine `if` guard around the assignment rather than a no-op reassignment. Centralizing it means a future fourth write site is the only way to bypass the gate, and the git second pass — which runs every 5s regardless of the parse gate — cannot defeat the parse-path gate a beat later by re-publishing identical branch/dirty values.
- [high] `applyGitInfo` now builds the merged array in a LOCAL `var merged = projects` copy and publishes once through the gate, instead of assigning `projects[index]` in a loop. **Why:** per-element subscript assignment on the observable is itself a published mutation (and one per project), so the previous shape published N times per tick unconditionally. Building locally makes the whole merge exactly one gated publish. Behavior is otherwise identical, including skipping results whose path no longer matches a project.
- [low] Added two test seams, `lastReloadDidPublishProjectsForTesting` (did the last publish attempt actually assign?) and `projectsPublishCountForTesting` (monotonic count of real assignments), plus `applyGitInfoForTesting` to drive the real main-thread git merge without spawning subprocesses. **Why:** a suppressed publish is invisible from `projects` alone — a correct suppression and a correct identical re-publish yield the same value — so the assertion needs a seam, following the `lastReloadParsedPathsForTesting` precedent from Step 3. Both seams are `@ObservationIgnored` so reading them never creates an observation dependency of its own.
- [high] Verified the gate is load-bearing by mutation-testing rather than trusting green tests. **Why:** a gate test that passes for the wrong reason is worthless. Deleting the `guard newValue != projects` produced 8 failures across `PlansStoreTests`; deleting the `sections` + `howProgress` comparisons from `Task.==` (simulating exactly the "sloppy hand-written `==` that misses a field" risk the step called out) produced 2 failures, including `testNestedOnlyChangePublishesAndSurfaces`. Both mutations were reverted and the suite re-verified green.
- [low] Did NOT touch `MenuBarLabel.swift`. **Why:** it re-bakes its `ImageRenderer` bitmap because `body` re-reads `store.iconSpaceCounts`, which is a computed property over `projects`; suppressing the `projects` publish removes the invalidation at the source, so no change to the label itself was needed. The task listed the file as "only touch if bitmap re-bake still churns after Step 4".
- [high] Step 2 throttle interval = **30 seconds** (`PlansStore.gitThrottleInterval`), the short end of the ~30-60s freshness lag the Assumptions already accept. **Why:** at the unchanged 5s poll interval this collapses 12 ticks' worth of git work into 1 — 24 spawns per 5s becomes 24 per 30s (~415k/day to ~69k/day, an ~83% cut) — while capping worst-case branch-indicator staleness at 30s. Going to 60s would save only a further ~8% of the original spawns while doubling the window in which the UI can display a wrong branch, which is a bad trade for a visible correctness property.
- [high] The real worst-case staleness window is 30s, but only for a branch switch made ENTIRELY outside the app that touches no `.plans/` file. **Why:** a project whose parse result changed on a tick bypasses the throttle and re-queries git immediately (condition 3 in `gitPathsToQueryThisTick`), and the common branch-change path in this app — a plan moving to in-progress as a worktree is created — necessarily rewrites `.plans/`, so it refreshes on the very next tick. A bare `git checkout` in a terminal with no plan edit is the only case that waits out the full window.
- [high] Injected the clock as a `now: () -> Date` closure on `PlansStore.init` (defaulting to `Date.init`) rather than calling `Date()` inside the throttle. **Why:** the step forbade an untestable throttle; a closure lets tests hold a mutable `TestClock` and step across the 30s boundary deterministically with zero real `sleep`, keeping the new tests as fast as the rest of the suite (~0.16s for all 58). Alternative considered and rejected: a `Clock`/protocol abstraction — more ceremony than a one-line closure for a single time read, and the codebase has no other time-source seam to be consistent with.
- [high] Throttle bookkeeping is a `gitQueryTimes: [String: Date]` map REBUILT against the live registry on every pass, exactly mirroring Step 3's `parseCache` rebuild. **Why:** a de-registered project loses its timestamp with it, so it cannot be throttled by a stale entry if re-registered later — it is queried immediately like any newly-registered project. Covered by `testDeregisteredProjectDoesNotResurrectStaleThrottleEntry`.
- [high] A skipped project carries its ORIGINAL query timestamp forward, never `now()`. **Why:** writing the current time on a skip would let repeated skips push the next query indefinitely into the future, turning the 30s window into an unbounded one and making the "wrong branch shown indefinitely" failure the step warned about actually reachable. Carrying the original makes 30s a hard ceiling.
- [high] Threading is untouched: the throttle only shrinks the `paths` array computed on the main thread BEFORE the existing `DispatchQueue.global(qos: .utility).async` hop, and `applyGitInfo`'s merge-by-path already skips projects absent from the results. **Why:** #059 was explicitly out of scope. Projects filtered out by the throttle keep their last-known branch/dirty because `performReload` carries git fields over via `priorGitInfo` — they are never reset to `nil` and never republished. Covered by `testThrottledTicksPreserveLastKnownGitValuesWithoutRepublishing`.
- [low] Added an early `guard !paths.isEmpty else { return }` so a fully throttled tick skips the background dispatch entirely. **Why:** on an idle tick with all projects throttled there is nothing to query, so the two queue hops (utility + back to main) and the resulting no-op `applyGitInfo` are pure waste. Placed AFTER `diagRecordGitSpawns(0)` so the diagnostic still emits its line for that tick.
- [low] Updated `diagRecordGitSpawns` to report `paths.count * 2` where `paths` is the POST-throttle queried set, not `projects.count * 2`. **Why:** Step 1's note said the diagnostic must report the actual spawns scheduled for the tick, and that number is how the final Step 5 re-measurement is verified; leaving the pre-throttle count would have made the diagnostic silently overstate spawns by up to 12x.
- [low] Added a `lastGitPassQueriedPathsForTesting` seam exposing which paths the last pass scheduled a query for. **Why:** a throttled tick is invisible from `projects` alone (a skipped query and a query returning identical values produce the same state), following the `lastReloadParsedPathsForTesting` precedent from Step 3.
- [high] Verified the throttle is load-bearing by mutation-testing, not by trusting green tests. **Why:** setting `gitThrottleInterval` to 0 produced 5 failures across the new git-pass tests; the file was then restored and verified byte-identical to its pre-mutation state and the suite re-run green.
