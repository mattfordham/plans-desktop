# Add Execute-More And Re-Elaborate Options For Plans In Review

**ID:** 091
**Created:** 2026-10-11T19:35
**Type:** feature
**Status:** completed

## What
Add the option to further execute plans. For example, if a plan is in "ready for review" (the `review`/`in-review` state), add an option to execute on that plan more. Elaborating on it should also move it back to pending — so add that too.

## Why
Today, once a plan reaches `review`/`in-review` (the terminal state an autonomous/worktree execution leaves it in), Surface B exposes **no** action for it except Delete — every gating predicate (`canWork`, `canElaborate`, `canExecutePending`, `canReElaborate`, `canBacklog`, `canRestore`) returns false for review states. The only way to iterate on a plan that's "ready for review" is to drop to the CLI. This task closes that gap on two fronts:

1. **Execute more** — surface an Execute action on review-state plans. plans-cc's `/plan-execute NNN` already *resumes* a `review`/`in-review` plan (plan-execute SKILL Step 6 flips it back to `in-progress`, reusing the kept worktree if present), so this is a pure UI/gating addition over the existing `.execute` run mode — no launcher change needed. It gives review plans the same one-click Execute that elaborated plans already enjoy (#078) and that pending plans got in #088.

2. **Re-elaborate (back to pending)** — surface a Refine action on review-state plans whose semantics, per the request, move the plan **back to pending** and re-run elaboration. This is NOT a built-in plans-cc capability: `/plan-elaborate` has no `review`/`in-review` input branch and never resets a later status (plan-elaborate SKILL Step 6 + Step 14 leave any status ≥ `elaborated` untouched; Path C explicitly does NOT change status). So it needs a dedicated launcher prompt that explicitly resets `**Status:**` to `pending` first, then elaborates — folding in the user's optional guidance. This lets a reviewer send a plan back to the drawing board from inside the app.

It reuses every established pattern: disjoint gating predicates (like `canExecutePending` sits beside `canWork`), paired row-action glyphs, the `ExecuteModal` (keep-only) and `ElaborateModal` (optional guidance + Deep) shapes, and a new `RunMode` + `run-task.ts` prompt kept in sync via `npm run build`.

## Assumptions
### Pre-execution (from elaboration)
- [low] Re-elaborate from review resets status to `pending` (not `elaborated`). **Why:** The request literally says "elaborating would move it back to pending." Resetting to pending then running `/plan-elaborate` naturally re-elaborates it to `elaborated`, matching the stated intent.
- [low] Implement the status reset via a new app-side Node run mode (`reviewReElaborate`) rather than editing the global `~/.claude/skills/plan-elaborate/SKILL.md`. **Why:** The SKILL file is a user-global file outside this repo; a repo task should not mutate global tooling. The launcher prompt instructs the agent to reset the header, keeping the behavior self-contained to the desktop app.
- [high] Execute-more reuses the existing `.execute` RunMode + keep-only `ExecuteModal` unchanged. **Why:** plan-execute SKILL Step 6 already resumes a `review`/`in-review` plan; no new mode is needed, matching the #078/#088 precedent.
- [high] Both `review` and `in-review` statuses receive the new actions. **Why:** They are the two terminal "ready for review" states; the request's "ready for review" covers both.

### Discovered during execution
- [low] Added `.reElaborateReview` to the existing `modeVerb` switch in `PlanDetailView.swift` (grouped with `.reElaborate` → "Refining"), not planned in steps 1–4. **Why:** the new enum case made that `switch run?.mode` non-exhaustive, breaking the build.
