# Add Elaborate Button For Elaborated Plans

## What
For elaborated plans, add an elaborate button. Clicking would open a modal similar to the capture modal, but would allow the user to further elaborate a plan with the entered text.

## Why
Adds value by letting a user steer further elaboration of an already-elaborated plan with their own guidance, without leaving the app or hand-editing the markdown. Today the only "Elaborate" action lives on *pending* tasks and takes no input; once a plan is elaborated the user can only Execute it. This closes the loop: an elaborated plan can be refined with extra context (new constraints, missed cases, a different direction) that the autonomous `plan-elaborate` Path-C ("further elaboration") flow then folds into the How/Verification/Impact sections.

## How Summary
Add a new `.reElaborate` run mode that, unlike every existing mode, carries BOTH an existing `--task-id` AND a free-text `--description`. The Swift `RunMode` currently uses a single `usesDescription` flag that conflates "has a description" with "has no task id"; split that so the spawn arg-shape can emit both flags for re-elaborate. Thread an optional `description` through `TaskRunner.run(...)` → `TaskRun` → `spawn(...)`. On the Node side, add a `reElaborate` mode to `run-task.ts` (and the bundled `dist`/app copies) whose prompt drives `plan-elaborate <id>` in Path-C further-elaboration mode using the user's text as the guidance. In the UI, add a single-field sheet (`ReElaborateModal`, modeled on `NewPlanModal` but stripped to one editor + submit/cancel) and a "Refine" button shown only for `.elaborated`, non-blocked tasks in both `PlanDetailView` and `ProjectCard`, gated by a new `canReElaborate` predicate. Add a progress-sheet verb for the new mode.

## Assumptions

### Initial (from elaboration)
- [low] Re-elaborate is modeled as a NEW `.reElaborate` `RunMode` that carries BOTH `--task-id` and `--description`, rather than overloading the existing `.elaborate` mode or appending the text to the file beforehand. **Why:** every current mode is either task-id-only or description-only; re-elaborate is the first hybrid. A dedicated mode keeps the contract explicit and unit-testable, and the Node side can craft a Path-C further-elaboration prompt distinct from the pending-task `.elaborate` prompt. The current single `usesDescription` flag conflates "has description" with "no task id", so it is split into `usesTaskID` + `usesDescription`.
- [low] The trigger is a separate single-field `ReElaborateModal` sheet (copied from `NewPlanModal`, stripped of project picker / toggles / image paste / draft persistence), not an inline popover and not a reuse of `NewPlanModal` with a flag. **Why:** the task says "modal similar to the capture modal"; a dedicated lightweight sheet matches that intent and avoids bloating `NewPlanModal`'s project-scoped capture logic with a task-scoped path.
- [low] The button is shown for `.elaborated` (non-blocked) tasks in BOTH `PlanDetailView` and `ProjectCard`, appearing alongside "Execute" (so an elaborated plan offers both Refine and Execute). **Why:** the elaborated state is exactly when further elaboration is meaningful; surfacing it in both places matches where the existing Elaborate/Execute buttons already live. No new status is introduced — the plan stays `elaborated` after refining.
- [low] In `ProjectCard`, the elaborated row will show BOTH a Refine glyph and the existing Execute glyph (in an `HStack` inside the fixed 22pt row height), rather than replacing Execute or hiding it behind a menu. **Why:** the detail view shows both, so the card should be consistent; the row's `else if` chain + single-glyph-height constraint means this needs a deliberate small layout (two glyphs in an HStack) to avoid changing row metrics — flagged so the executor sizes it carefully.
- [low] Re-elaborate text is NOT persisted as a draft. **Why:** the existing draft infrastructure in `PlansStore` is keyed per-project for capture; re-elaborate is a quick, task-scoped refinement, so per-task draft persistence is deferred as out of scope for v1 to keep the change small. Can be added later if desired.
- [high] The Node `run-task.js` is regenerated from `run-task.ts` via `npm run build` (esbuild) and never hand-edited; both `dist/` and the app-bundled copy are refreshed by the build. **Why:** the existing `dist/run-task.js` is clearly an esbuild artifact of `run-task.ts` (matching headers/structure), and `package.json` defines `"build": "node build.mjs"` — editing the generated file would be overwritten on the next build.
- [high] `plan-elaborate` supports "further elaboration" of an already-elaborated task (its Path C), so the re-elaborate prompt drives `/plan-elaborate <id>` autonomously and folds the user's text in as guidance, leaving the task `elaborated`. **Why:** the plan-elaborate skill documents Path C ("task already elaborated or in-progress") explicitly, which is the exact contract this feature relies on.
