## What
Better layout for cards. Top align within grid. Adjust columns count based on window width.

The dashboard (`BrowserWindow.cardGrid`) renders project cards in a `LazyVGrid` with a hardcoded 3 flexible columns. At narrow widths 3 columns get cramped; at very wide widths they get sparse/overlong. Cards in the same row also visually stretch when row heights differ. Goal: anchor cards to the top of each grid row and make the column count adapt to the available width.

## Why
Improves maintainability and usability by replacing the hardcoded 3-column grid with a responsive layout that adapts to window width, and by anchoring cards to the top of each row so rows with uneven card heights read cleanly instead of cards floating/stretching.

## How
- [x] Step 1: Add layout constants near the top of `BrowserWindow` (e.g. `cardMinWidth`, `gridSpacing = 16`, `gridPadding = 16`) so the grid math has single sources of truth instead of magic `16`/`3` literals scattered in `cardGrid` (`Sources/Plans/BrowserWindow.swift:96-111`).
- [x] Step 2: Add a pure helper `private func columnCount(forWidth:) -> Int` in `BrowserWindow` that computes `max(1, Int((width - 2*gridPadding) / (cardMinWidth + gridSpacing)))`. Pure function so it is unit-testable.
- [x] Step 3: Wrap the `LazyVGrid` in a `GeometryReader` (reading the `ScrollView`'s width) and build `columns` from `columnCount(forWidth:)` instead of the hardcoded `count: 3`. Keep `GridItem(.flexible(), spacing: gridSpacing)` so columns still share width evenly. Guard against layout loops — only the width is read; column count is the sole derived value. (`Sources/Plans/BrowserWindow.swift:96-110`)
- [x] Step 4: Set the `LazyVGrid` `alignment:` parameter to `.top` so cells in a row anchor to the top, and confirm `ProjectCard` does NOT force vertical fill — `ProjectCard.swift:52` should stay `maxWidth: .infinity` (no `maxHeight: .infinity`) so each card sizes to its content and top-aligns naturally. (`Sources/Plans/ProjectCard.swift:52`)
- [x] Step 5: Add unit tests for `columnCount(forWidth:)` in `Tests/PlansTests/` covering: a width that yields 1 column (narrow), the ~820 min-width case, and a wide width yielding ≥4 columns. (`Tests/PlansTests/`)
- [x] 👁 Step 6: Build and run the app; resize the window from minimum (820pt) to wide and confirm columns reflow (1→2→3→4…), cards stay top-anchored within rows, and the §004 scroll-to-project drill-down still anchors correctly after the grid restructure. **User-confirmed** after fix round 1 (min-width lowered, cardMinWidth=400, top-align via Spacer wrapper).

## Assumptions

### Initial (from elaboration)
- [low] Use a fluid "fit as many cards as fit" column algorithm (computed count from a minimum card width) rather than fixed breakpoints. **Why:** Research presented both; fluid keeps cards within a readable min width at any size and avoids hand-tuned breakpoint thresholds, matching the existing `.flexible()` even-share intent.
- [low] Use `cardMinWidth` ≈ 260pt as the responsive minimum. **Why:** Research estimate based on the card's icon + name + status-badge header; no existing layout constant to reuse, so flagged for review during the §6 observation step.
- [low] Use `GeometryReader` to read available width rather than `containerRelativeFrame`. **Why:** Research noted both work on macOS 15; GeometryReader is the more familiar pattern and the read here is narrow (width only → column count), keeping layout-loop risk low. Revisit if a loop appears.
- [high] Keep cards content-sized (no `maxHeight: .infinity`) and top-align rows via the grid's `alignment: .top`. **Why:** `ProjectCard.swift:52` already sizes to content; LazyVGrid rows top-align cells by default, so this is the minimal change that satisfies "top align within grid" without forcing uniform card heights.

### Discovered during execution
- [low] Used `cardMinWidth = 260pt` as planned. **Why:** Estimate from the card header (icon + name + status badges); flagged for confirmation at the §6 observation step.
- [low] Measured viewport width via a `GeometryReader` width probe in the `ScrollView`'s `.background`, pushing the width through a `GridWidthKey` preference into a `@State gridWidth`. **Why:** Reading width in `.background` keeps it out of the scroll content's intrinsic vertical layout, avoiding the greedy-GeometryReader-in-ScrollView zero-height/layout-loop trap; only width is read and the column count is the sole derived value. Chosen over a direct GeometryReader wrap (collapses height) and over `containerRelativeFrame` (less explicit).
- [high] Made `columnCount(forWidth:)` a `static` method and the layout constants `static let` with default (internal) access. **Why:** A pure width→count function has no reason to be an instance method, and `internal`/`static` makes it trivially callable from the test target via `@testable import` without instantiating the SwiftUI view.
- [high] Left `LazyVGrid` `alignment` at its default `.center` rather than setting `.top`. **Why:** `LazyVGrid`'s `alignment:` is a `HorizontalAlignment` (`.top` does not exist there and fails to compile); vertical top-anchoring of cells within a row is the LazyVGrid DEFAULT and is satisfied by keeping cards content-sized (no `maxHeight: .infinity` on `ProjectCard.swift:52`). The plan's "set alignment to .top" step was based on an incorrect assumption about that parameter's axis.
- [high] Added a private `GridWidthKey: PreferenceKey` type in `BrowserWindow.swift` to carry the measured width. **Why:** Required by the preference-key width-probe approach; scoped `private` to the file.
- [high] Chose test widths 300pt and 50pt (both → 1 column, the latter asserting the `max(1,…)` floor holds), 820pt (the window minimum → EXACTLY 2 columns by the formula, not 3), and 1400pt (→ 4 columns). **Why:** Each width lands clearly inside an Int-quotient bucket (not on a boundary) so the assertions are robust to no rounding ambiguity; 820pt matches the `.frame(minWidth: 820)` so the test pins the real minimum-window behavior, and 1400pt satisfies the segment's "≥4 columns" requirement.
- [high] Did not add an explicit `import CoreGraphics`/`SwiftUI` to the test file. **Why:** `import XCTest` + `@testable import Plans` already transitively expose `CGFloat`; the filtered test build compiled and passed with plain `CGFloat` literals, so no extra import was warranted.
- [high] Fixed the top-align bug (Issue 1) by wrapping each card in `VStack(spacing: 0) { ProjectCard(...); Spacer(minLength: 0) }` and moving `.id(project.projectPath)` onto that wrapper. **Why:** LazyVGrid sizes every cell to its ROW's max height, so a content-sized card alone still gets a stretched cell — but the card's `.background`/`.overlay` chrome was being painted on the stretched frame, filling the cell. Pairing the content-sized card with a trailing `Spacer` lets the spacer absorb the slack so the card's chrome hugs its content and pins to the top. Deliberately did NOT add `maxHeight: .infinity` to `ProjectCard` (that would re-introduce the stretch). The `.id` stays on the wrapper so the §004 ScrollViewReader drill-down still scrolls to the cell. (Corrects the earlier "[high] Left LazyVGrid alignment at default" assumption — content-sizing alone did NOT top-anchor; the visible chrome still stretched, which was the reported bug.)
- [low] Set window `minWidth` to `480` (from `820`), keeping `minHeight: 520`. **Why:** Issue 2 wants the window draggable narrow enough for a 1-column layout. 480pt comfortably fits one 400pt card plus 2×16pt grid padding (432pt) and window chrome, while staying a sane minimum. Value is a judgment call flagged for confirmation at the observation step.
- [high] Changed `cardMinWidth` 260→400 (Issue 3) and recomputed the 4 columnCount tests against the new formula `max(1, Int((width - 32) / 416))`: 300→1, 50→1, 820→1 (was 2; retargeted the "two columns" case to 1000→2 since 820 now yields 1), 2000→4 (was 1400; 1400 now yields 3, so widened to 2000 to keep a clear ≥4 assertion). **Why:** The segment requires every assertion to reflect the true computed value of the new formula; each chosen width lands clearly inside an Int-quotient bucket, not on a boundary.
- [high] (§6 follow-up / in-card row alignment) Converted the per-card plan-row list from `VStack { HStack-per-row }` to a SwiftUI `Grid(alignment: .topLeading, horizontalSpacing: 8, verticalSpacing: 2)` with one `GridRow` of FOUR cells per plan (status-icon / id / [type] / title). **Why:** Grid auto-sizes each column to the widest cell across ALL rows, so the id / [type] / title columns share a consistent left edge on every row — the requested table look. `.topLeading` keeps multi-line titles top-aligned with the icon as before.
- [high] Handled the nil `[type]` cell by ALWAYS emitting a single monospaced `Text(row.type.map { "[\($0.label)]" } ?? "")` (empty string when no type) rather than a conditional `if let`. **Why:** A conditional would omit column 3 on type-less rows and break Grid's per-column alignment; one always-present Text cell keeps exactly four cells in every GridRow so the column exists and aligns. Avoided the `Color.clear.frame(width:0)` placeholder noted as unreliable in the segment.
- [high] Attached the row tap target + selection highlight PER-CELL (a private `View.rowChrome(isSelected:onTap:)` extension applying `.padding(.vertical,5)`, `.frame(maxHeight:.infinity)`, the accent `.background`, `.contentShape(Rectangle())`, and `.onTapGesture`) instead of wrapping the GridRow in a Button or applying a single row-spanning background. **Why:** Wrapping a GridRow in a Button defeats Grid's cross-row column sizing, and `GridRow` does not reliably accept a row-spanning `.background`/`.onTapGesture`/`.padding`. Per-cell chrome makes the WHOLE row clickable and highlighted and keeps column participation intact. Trade-off: the highlight shows tiny 8pt gaps at the `horizontalSpacing` between cells rather than one continuous pill — flagged for visual confirmation at re-observation. `.frame(maxHeight:.infinity)` makes every cell's background fill the row's full height so the highlight bands line up vertically.
- [high] (continuous-highlight fix) Replaced the per-cell `rowChrome` highlight with a SINGLE row-spanning highlight applied to the whole `GridRow`, using the **`horizontalSpacing: 0` + per-cell trailing padding** technique: set the enclosing `Grid` to `horizontalSpacing: 0` and recreated the inter-column gap with `.padding(.trailing, 8)` on cells 1–3; the GridRow itself carries `.frame(maxHeight:.infinity)`, `.padding(.vertical,5)`, a `RoundedRectangle(cornerRadius:6)` `.background`, `.contentShape(Rectangle())`, and `.onTapGesture`. **Why:** This chosen technique (over the GridRow `.background` with non-zero spacing) is the verifiably gap-free one — with zero Grid spacing there is NO inter-column gap for the background to break across, so the highlight renders as ONE continuous rounded pill spanning the full row width while the visual column spacing is preserved by the trailing padding. The previously-noted 8pt-gap trade-off is eliminated. Column alignment, the always-present empty `[type]` cell, multi-line title top-alignment, and whole-row clickability are all preserved. The now-unused `View.rowChrome` extension was REMOVED to avoid dead code. `swift build` green; `BrowserWindowTests` 28/28 pass.
