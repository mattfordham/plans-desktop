# Add Direct-Execute Option For Un-Elaborated Plans

**ID:** 088

## What
For un-elaborated plans. Add an option to directly execute them as opposed to just elaborate them. The direct execution option should also come with a field for additional prompting and for a deep option.

## Why
Today a pending (un-elaborated) plan in Surface B offers only the Elaborate action — the user has to elaborate, wait, then come back and Execute as two separate steps. This adds a second action on pending rows that drives the whole pipeline in one go: hand the plan straight off to `plan-execute`, which auto-elaborates it inline (optionally with extra guidance and the Deep reasoning pass) and then implements it in an isolated worktree, leaving it in `review`. It gives pending plans parity with the one-click Execute that elaborated plans already have (#078), and reuses the optional-guidance + Deep dialog pattern established for Elaborate (#074).

## How Summary
Add a direct-Execute action for pending plans that reuses the existing `.execute` run path end-to-end, newly opened up to carry free-text guidance. Flip `RunMode.execute.usesDescription` to `true` (the `spawn` arg-assembler already emits `--description` for any `usesDescription` mode, and already emits `--deep`/`--keep`), relax `run-task.ts`'s `execute` branch to accept an OPTIONAL `--description`, and extend `buildExecutePrompt` to (a) fold that guidance into a `"""` block and (b) instruct the agent to auto-elaborate the pending plan first (choosing "Elaborate now" at `plan-execute`'s not-elaborated gate, deep when `--deep` is set) before executing — so Deep and the guidance always have an elaboration pass to act on. On the UI side, add a `canExecutePending` predicate (pending + non-blocked, mirroring `canElaborate`), render a second `play.fill` glyph next to the Elaborate glyph on pending rows (and a sibling header button in the detail view), and present a new `ExecutePendingModal` — an `ElaborateModal` clone (optional `PlanTextEditor` guidance + always-enabled Deep toggle) that also carries the Keep toggle from `ExecuteModal`, submitting via `runner.run(... mode: .execute, description:, deep:, keep:)`.

## Assumptions

### Initial (from elaboration)
- [low] "Direct execute" auto-elaborates the pending plan inline (choosing "Elaborate now" at `plan-execute`'s not-elaborated gate) and THEN executes, rather than skipping elaboration entirely. **Why:** the task also asks for a "deep option," and plans-cc `--deep` only affects an *elaboration* pass; skipping elaboration would leave Deep (and the guidance) with nothing to act on and no How checklist to execute. Auto-elaborate-then-execute is the only interpretation that honors all three requested controls, and it maps onto `plan-execute`'s existing step-7a "Execute anyway/Elaborate now" gate.
- [low] Reuse the existing `.execute` RunMode (opening its description channel) rather than adding a new mode. **Why:** `spawn` already emits `--description`/`--deep`/`--keep` for `.execute`'s siblings, `run(...)`/`TaskRun` already carry all three, and #078 already routes the Execute dialog through `.execute` — a new mode would duplicate that plumbing for no behavioral gain.
- [low] Create a new `ExecutePendingModal` instead of extending `ExecuteModal`. **Why:** `ExecuteModal` is deliberately Keep-only with a doc comment arguing AGAINST a guidance box; cloning `ElaborateModal` (which already has the optional guidance + Deep + image-paste pattern) and adding Keep is cleaner and keeps the elaborated-plan Execute dialog pristine.
- [low] Pending rows show Elaborate AND direct-Execute side by side (a tight `play.fill` pair), rather than replacing Elaborate. **Why:** the task says "add an option," implying both paths remain available; this mirrors the elaborated-row Refine+Execute pair exactly.
- [high] `canWork` stays elaborated-only (in-progress excluded) and the new direct-execute path is a separate `canExecutePending` predicate. **Why:** #027 deliberately removed Execute from in-progress plans; relaxing `canWork` would regress that, so a disjoint predicate keeps that guarantee while adding the pending path.
- [low] No automated test is added for `run-task.ts` (verified via `npm run build` compile only). **Why:** there is no TS test harness in the repo (`Tools/work-task` has only a `build` script, no test runner), matching #074's actual outcome where the TS arg-shape test was aspirational.

### Discovered during execution
- [high] The pre-existing `testRunModeUsesDescriptionFlag` test had to be edited, not just added to: it hard-asserted `XCTAssertFalse(RunMode.execute.usesDescription)`, which segment 1's flip (Step 1) made false. Moved `.execute` to the true group and updated the doc comment. **Why:** leaving the old assertion would have failed the suite after Step 1; the flag flip is intentional, so the assertion must follow it. (Not a new file beyond the segment's listed scope — same `TaskRunnerTests.swift`.)
- [low] Placed the pending direct-Execute glyph as the SECOND glyph in the pending row's `HStack(spacing: -4)` (Elaborate first, `play.fill` second), matching the elaborated row's Refine-then-Execute order. **Why:** keeps the `play.fill` Execute glyph in the same trailing position across pending and elaborated rows, so the direct-Execute affordance sits consistently for the eye.
- [low] In `PlanDetailView`'s header, the direct-Execute button renders between the Elaborate and Refine buttons (Elaborate → Execute → Refine → elaborated-Execute). For a pending plan only Elaborate+Execute are gated on, so the user sees "Elaborate  Execute"; the Refine/elaborated-Execute buttons never co-occur with the pending pair. **Why:** inserting right after Elaborate satisfies the step's "right after the Elaborate button" instruction while keeping each button's status gate independent.
