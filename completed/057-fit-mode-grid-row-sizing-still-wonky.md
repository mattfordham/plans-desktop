# Fit-Mode Grid Row Sizing Still Wonky

**ID:** 057
**Created:** 2026-06-23T00:00
**Type:** bug
**Status:** completed
**Completed:** 2026-06-23T15:20
**Branch:** fix/057-fit-mode-grid-row-sizing-still-wonky

## What
The row sizing in the card grid remains wonky. In the screenshot, the lower row would be expected to grow bigger (taller) than it does. The fit-mode grid row-height logic isn't producing the expected result.

Reference screenshot: top row holds "Client A" (a tall project card with many tasks) and "Plans" (a short card with 2 tasks); the bottom row holds "Client B Website" (2 tasks) and "Plans Desktop" (1 task). The expectation is that the lower row should grow bigger, but it doesn't.

## Why
Improves the fit-mode grid's use of vertical space and matches user expectation: a less-full row should expand to absorb the leftover slack rather than leaving a band of empty space below it. Today the bottom (shorter) row barely grows because the current "water-fill" stretch only levels shorter rows *up toward* the tallest row's natural height and never beyond — so when the top row is very tall, almost all the budget is already consumed by it and the bottom row gets little slack.

## How Summary
The bug is conceptual, not a timing/measurement glitch. `stretchShorterRows` (the `#055` water-fill in `BrowserWindow.swift`) raises the shortest rows to a common level `L` chosen so `sum(max(natural_i, L)) == availableForRows`, keeping the tallest row at its natural height. With one very tall row (Client A), `L` lands at or below that tall row's natural height, so the short bottom row only ever reaches ~the tall row's height — not "bigger." That was the *intended* behavior of `81f824e` ("so tall row isn't exaggerated"), but it is the opposite of the user's current expectation that the shorter row should grow to fill the empty space.

The fix is to change the stretch policy so leftover slack flows to the *shorter* rows preferentially — i.e. distribute the slack so shorter rows can grow past the tallest row's natural height (capped only by the per-row share of the viewport), pinning the tall row near its natural height and letting the short row consume the remaining budget. This is a new pure helper alongside `stretchShorterRows`, swapped into the `factor >= 1` stretch branch of `fitRowHeights`, fully unit-tested. The shrink path (`factor < 1`) is unchanged.

### Discovered during execution
- [low] Implemented `fillShorterRows` as the literal formula from the Step 2 design note: each row's final height is `min(max(natural_i, L), max(natural_i, share))`, where `share = availableForRows / rowCount` and `L` is the uncapped water-level solving `sum(max(natural_i, L)) == availableForRows`. **Why:** This is the exact formulation the task suggested and it is total + satisfies all four invariants (fills budget exactly when slack exists, never below natural, returns naturals when no slack, `[]` for empty).
- [low] DISCOVERED that this capped formula is mathematically IDENTICAL to the old `stretchShorterRows` for every input: the uncapped water-level `L` can never exceed `share` (when a tall row sits at natural above the average it pulls the level for the other rows BELOW `share`), so the `max(natural_i, share)` cap never actually bites. Verified numerically across many cases (`[350,180]`, `[350,150,130]`, `[500,100,100]`, large-slack/ballooning cases) — old and new produce bit-identical results. **Why:** Water-fill already directs ALL slack into the shortest rows first and only equalizes everything to `share` in the surplus regime, so a per-row cap at `share` is redundant. The visible "band beneath the short row" the user reported cannot be produced by the old water-fill when rows fill the viewport (the rows always sum to the budget exactly).
- [low] CONSEQUENCE: it is mathematically impossible (for a single tall + single short row under the exact-fill invariant) for the short row to end up STRICTLY TALLER than the tall row's natural height while the tall row stays at natural — the unique total-preserving solution makes them EQUAL (both at `share`) in the surplus regime. The Step 1 tests therefore assert the achievable, equivalent properties (short row absorbs the slack first / rises at least to the tall row's natural in the surplus regime, total fills the viewport exactly, never below natural) rather than a strict `short > tallNatural`. **Why:** Asserting the impossible would make the suite permanently un-greenable; the observation step (Step 5, the user's) will judge the visual result and can revisit the policy (e.g. a deliberately OVER-filling `max(natural_i, share)` that breaks exact-fill) if the band is still visible.
- [high] Because the new helper is numerically identical to `stretchShorterRows`, the four "old" stretch tests (`...LevelsShorterRowsUp`, `...SlackGoesToShortRowFirst`, `...SurplusBeyondGapLevelsAllRows`, `...FillsViewportAndNeverBelowNatural`) DO NOT conflict and were left passing as-is. **Why:** They encode invariants (fills viewport, never below natural, slack-to-short-first, surplus-levels-all) that the new policy also honors; no assertion contradicts the new behavior, so deleting/rewriting them would lose coverage for no benefit.
- [high] RETIRED `stretchShorterRows` and routed the `factor >= 1` branch through the new `fillShorterRows`; no other references remained (grep-verified) so the old helper was removed to avoid dead code. **Why:** Avoids two helpers with identical behavior; the new name documents the (intended) policy.

#### Revision 1 (over-fill policy — itself now superseded by Revision 2 above)
- [high] Per the user's design decision, `fillShorterRows` now implements the OVER-FILL policy `height_i = max(natural_i, share)`, `share = availableForRows / rowCount`. Short rows grow to `share` even PAST the tall row's natural height; tall rows (above `share`) stay at natural; the total MAY exceed `availableForRows` and the surrounding ScrollView absorbs the surplus. This DELIBERATELY abandons the exact-fill invariant on the stretch path — that is the whole point: it is what visibly lifts the short row and kills the empty band the old (mathematically no-op) water-fill could never remove. The dead water-level/suffix-sum machinery was deleted. **Why:** The prior pass proved the capped water-fill was bit-identical to the old behavior, so the band persisted; over-fill is the simplest monotonic, total formula that actually grows the short row.
- [high] EXACT-FIT BOUNDARY DECISION: kept the `guard availableForRows > naturalTotal else { return naturalRowHeights }` gate in `fillShorterRows` (real-slack-only), so the over-fill only fires when there is genuine slack. `fitRowHeights` enters the stretch branch on `factor >= 1` (i.e. `availableForRows >= naturalTotal`, including `==`); at exact fit (`factor == 1`) the gate is false and the helper returns the naturals UNCHANGED. Without this gate, `testFitRowHeightsExactFitLeavesRowsUnchanged` (viewport 1000, naturals `[571.2, 380.8]`, share = 476) would break because `max(380.8, 476) = 476` would over-fill the short row. The gate preserves that test while still letting any real-slack case over-fill. **Why:** Exact-fit must stay a no-op; the over-fill is only meaningful when there is slack to lift a short row into.
