## What
Desktop app support for plans-cc "branch mode" (.plans/ tracked on a dedicated orphan `plans` branch checked out as a permanent git worktree at <root>/.plans, gitignored on code branches; being built in plans-cc separately). App tweaks: (1) detect branch mode per project (git -C .plans rev-parse --show-toplevel == realpath(.plans)); (2) debounced background sync on the polling loop (git -C .plans pull --rebase, push) so plans written remotely appear without a local plans-cc run, never colliding with in-flight runs; (3) sync-status indicator on the project card (ahead/behind/conflict/offline); (4) optional "Convert to tracked plans" action that invokes the plans-cc migration; (5) update desktop-app-spec.md Data Contract 2 to describe branch mode; (6) verify reading, captures, and worktree execution via the .plans symlink still work. Contract details are provisional pending the plans-cc work — will re-elaborate to align once it lands.

## Why
Plans for some projects are moving into git (plans-cc "branch mode": an orphan `plans` branch checked out as a permanent worktree at `<root>/.plans`) so they can be read and written remotely. The app must keep reading, capturing and running plans unchanged in that layout, pull in plans written elsewhere without waiting for a local plans-cc run, and make sync health visible so a stuck rebase or failed push doesn't go unnoticed.

## How Summary
Mirror plans-cc's shipped branch-mode contract in Swift. A port of `detectMode` + `syncStatus` (`~/.claude/plans-cc/lib/plans-git.js`) runs in the existing throttled git second pass and adds mode, upstream, ahead/behind and stuck-rebase status to each project. A debounced scheduler shells out to the plans-cc-owned `plans-git.js sync`, skipping projects with a run in flight, a held `.plans/.git-lock`, or a conflict from the last sync. The app maps the helper's `Warning:` / `Renumbered` lines to a sync outcome. A sync glyph joins the card's git footer, mirroring the terminal dashboard's `plans:` line. A confirmed "Convert to tracked plans" card action runs `plans-git.js migrate` for local-mode projects. The spec documents storage modes and sanctions the helper (sync + migrate) as a subprocess writer.

### Discovered during execution
- [low] `PlansSyncStatus.upstream` is a `Bool` (plus a separate `remote` string), not the upstream ref name. **Why:** a faithful port of `syncStatus`, which returns `upstream: true/false` and `remote` from config; the ref name isn't needed for the indicator.
- [low] `GitHelper.plansSyncStatus(at:mode:)` takes an optional already-resolved mode so the store's git pass doesn't run `detectMode` twice per branch-mode project. Called without it, it re-detects exactly like `syncStatus`. **Why:** saves 2-3 git spawns per branch project per pass without changing behavior.
- [low] The shared runner's default timeout is 10s; on timeout the child is SIGTERMed and the query returns `nil` ("unknown"). Pipes are drained concurrently, and the result waits at most 1s more for pipe EOF so a grandchild holding the pipe can't stall it. **Why:** these are local, read-only commands, so 10s means wedged. The value wasn't specified.
- [low] The storage-mode and sync-status queries run inside the existing per-path git throttle (first sight, `.plans/` signature change, or 30s window) instead of a separate cache. Their last-known values carry over on re-parse the same way branch/dirty do. **Why:** this is the "cached; refreshed on signature change or the 30s window" behavior the step asks for, and it reuses the tested throttle instead of adding a second one.
- [high] The prior-git carry-over and background results now share one `PlansStore.GitResult` struct (made internal, with defaulted `mode`/`sync`) instead of the `(String?, Bool?)` tuple. The tuple-based test hooks still exist as thin adapters. **Why:** the tuple couldn't carry the new fields; existing tests stay unchanged.
- [low] `TaskRun.runProjectPath` is computed as `projectPath ?? <start path>`, and `hasRunningRun(inProject:)` compares standardized paths (`URL.standardizedFileURL`, which does not resolve symlinks). **Why:** run paths and registry paths come from the same registry strings, so standardization only guards trailing slashes and `.` components. Resolving symlinks on the main actor each poll seemed unnecessary.
- [high] The `PlansStorageMode` / `PlansSyncStatus` types live in `TaskParser.swift` next to `ProjectTasks`, as Foundation-only value types. **Why:** the same placement as the other `ProjectTasks` field types, and `GitHelper` needs them from Step 1.
- [low] `GitHelper.run` gained optional `environment:` and `currentDirectory:` parameters so `PlansGitHelper` reuses the shared runner (timeout, drained pipes, `GIT_TERMINAL_PROMPT=0`) and doesn't duplicate it. **Why:** the helper needs the login-shell PATH, `GIT_SSH_COMMAND` and cwd = project root. The defaults leave every git call unchanged.
- [low] The sync outcome is classified by priority conflict > locked > failed > synced. Only warnings starting `plans sync failed` or `plans-git failed` count as `.failed`. Other warnings (a failed push, a renumber left to resolve by hand, the git_commits notice) keep `.synced`, but every warning text is kept in `SyncResult.warnings` for the tooltip. `.conflict` carries no payload; its text is in `warnings`. **Why:** a failed push already shows as "ahead" and the helper retries it on the next commit, so calling it a sync failure would be noisy.
- [low] Helper timeouts are 60s for `sync` and 180s for `migrate`. A missing node, a launch failure or a timeout maps to `.failed(msg)` for sync and to `.error(msg, backupPath: nil)` for migrate. Migrate output with no `OK:`/`Error:` line becomes an error carrying the last warning. **Why:** the values weren't specified; batch-mode ssh makes an unreachable remote fail fast, so these only bound a wedged transfer.
- [low] Scheduler gates by trigger. `.scheduled` gets every gate, including the 90s debounce. `.runFinished` skips only the debounce. `.manual` (`syncNow`) skips the debounce, the auto-sync flag, the conflict back-off and the lock check, since the helper reports `.locked` itself. It still refuses in-flight, non-branch, no-upstream (or unknown status), rebase-stuck and busy projects. **Why:** a manual sync during a stuck rebase would let the helper `rebase --abort` the user's in-progress resolution, and a manual sync during a run could race the run's plans commits.
- [low] A `.plans/.git-lock` only blocks automatic sync while it is younger than 60s (plans-cc's `lockStaleMs`), compared on the injected clock. **Why:** the helper breaks older locks itself, so skipping on any lock would stall sync forever after a crashed commit.
- [low] The scheduler runs at the end of every reload (sync and async poll paths), not from the git pass. Syncs run concurrently on a global utility queue, one per project at most. A finished sync forces a git re-query for that path only, but does not force a reload; the next 5s poll picks up pulled files through the signature change. **Why:** this is the cheapest hook that sees fresh mode/status. Branch-mode project counts are small, so serializing syncs wasn't worth a manual sync queuing behind slow ones.
- [low] `TaskRunner.onAnyRunFinished` now passes the finished run's project path (`(String) -> Void`), so the app can sync just that project. `AppDelegate` wires `store.isProjectBusy` to `hasRunningRun(inProject:)`. **Why:** the no-argument callback couldn't tell which project to sync, and syncing every branch project on any run finish would spawn needless node processes. No test covers the one-line plumbing: `start()` spawns real node, so there's no seam.
- [low] Auto-sync is a store-level observable `autoSyncEnabled` persisted under UserDefaults key `autoSyncPlans` (missing key reads as on). There is no UI toggle yet. **Why:** the step asked only for the flag. A settings surface is a UX call left for later.
- [low] The card shows ONE sync glyph, picking the most severe mark: syncing → rebase stuck → last-sync conflict → no upstream → failed (including a missing helper) → ↑n/↓n → ✓. The dashboard's `buildPlansLine` instead lists every mark side by side, and the tooltip carries the rest. A `.locked` outcome isn't surfaced at all, since it only means another plans-cc commit held the lock. "Syncing" outranks everything so a manual retry gives visible feedback. **Why:** a footer glyph has room for one mark. The order is the step's own, plus syncing.
- [low] Sync glyph colors come from the dashboard palette: `blocked` #cc6666 for conflict/rebase stuck, `dirty` #fabd2f for no upstream, failed and ahead/behind, `clean` #8ec07c for in sync, and `label` #a89984 while syncing. A failed sync is amber, not red. **Why:** offline is the common failure and clears on its own, so red is kept for states that need a manual fix.
- [low] The card's "existing actions" have no card-level menu, so "Sync plans now" and "Convert to tracked plans…" live in a new `.contextMenu` on the card footer (right-click). Tapping the sync glyph also syncs now when a manual sync is allowed. **Why:** this is the least intrusive place, and local-mode cards gain no visible chrome. A visible Convert button would be a UX call.
- [low] Remote presence uses a new `GitHelper.hasRemote(at:)` (`git remote` non-empty), queried in the git second pass only for local-mode projects. It's carried as `ProjectTasks.gitHasRemote` / `GitResult.hasRemote` through every rebuild. The `/plan-init` skill checks `git remote get-url origin` specifically; the app accepts any remote, as the step notes suggested. **Why:** it costs one spawn per local project per throttle window and no extra machinery. `migrate` itself handles a missing `origin` by skipping the push.
- [low] Migrate pauses its path through a store-level observable `pausedPaths`. While paused, the reload keeps the last parse and skips the signature listing. The project also stays listed even though the registry reader drops entries whose `.plans` is missing, so the card doesn't vanish mid-migrate. The git pass skips the path, git results that land late for it are dropped, and every sync trigger returns `.paused`. On finish, whether OK or Error, the path is unpaused and its git/mode is force-re-queried. **Why:** the registry's `.plans`-exists filter would otherwise drop the card, and with it the path's per-path sync/throttle state, while `.plans` is moved aside.
- [low] Convert availability is `PlansStore.convertSkipReason`, checked in this order: paused → not local → no (or unknown) remote → busy. The store refuses to start a migrate that fails it, so the card's visibility and the action share one rule. Starting a run in the project while a migrate is in progress is not blocked. **Why:** the step only gated the action's visibility. Blocking run starts would touch TaskRunner and the modals, which are outside this segment's scope.
- [high] The parser needed no change for the branch-mode entries. It lists only `*.md` files directly inside `pending/`, `completed/` and `backlog/`, and the signature covers only those three directories. A new pinning test, `TaskParserTests.testBranchModeWorktreeEntriesAreIgnored`, covers a `.git` file, `.gitignore`, `.gitattributes`, a `config.json` `sync` key, `.git-lock/` holding a stray `.md`, and `archive/2025/*.md`. It asserts no phantom tasks and an unchanged signature. **Why:** the test passed on first run, so there was no RED. It pins existing behavior rather than driving a fix.
- [low] The spec lists `archive/` as an entry the parser ignores, even though plans-cc's `TASK_DIRS` includes it. plans-cc uses `archive/` only for the id scan, and the reference parser `lib/parse-tasks.js` doesn't read it either. The spec presents `backlog/` as a normal task directory, not an ignored entry. **Why:** the step's list grouped `backlog/` with the ignored entries, but the app has parsed `backlog/` since #077. Calling it ignored would contradict §5.1/§5.5.
