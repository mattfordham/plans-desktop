# Fix Agent Panel Getting Clipped On Bottom Half

**ID:** 121

## What
Agent panel getting clipped sometimes on bottom half. Note in screenshot how the last line of text is cropped.

![pasted image](file://~/Library/Application%20Support/Plans/attachments/9A38D41B-B91D-4370-B4EF-6A1917737E9B.png)

## Why
Improves reliability and clarity by making the agent dock show only the **active / most-recent action** instead of an ever-growing stack of every past run. The reported "clipped bottom half" is a downstream symptom: the dock transcript (`PlanAgent.transcript`) appends a `.run` segment for every action — elaborate, execute, review, capture — and **never prunes finished ones** (by explicit, currently-tested design), so a plan worked repeatedly accumulates stacked run logs whose total height exceeds the persisted `agentDockHeight` cap and the newest content ends up cropped at the dock's bottom edge. "New conversation" clears only discuss turns, so the user has no affordance to shrink the stack. Refreshing the run view with each action — keeping only the active/most-recent run segment, as the user expects — removes the root cause of the over-tall transcript (and therefore the clipping), not just the visible band.

## How Summary
Primary fix (behavioural): make the dock "refresh" its run view with each action by pruning finished `.run` segments from `PlanAgent.transcript` when a new run begins, so only the **active/most-recent run** (plus the current conversation's discuss turns) is ever rendered. Today `beginRunSegment` is append-only and no UI path prunes prior runs, so the transcript grows without bound across elaborate→execute→review and eventually overflows the persisted `agentDockHeight` cap, cropping the newest line. The change is made in the model (`PlanAgent`) — the single source of truth the dock renders — not in layout, so it is inherently #096-safe (no size measurement). This inverts the previously-tested "continuous history accumulates" contract, so `PlanAgent`'s class doc and the `PlanAgentTests` that lock in the append-and-keep behaviour must be updated deliberately.

Defensive fix (layout, retained from the prior pass): keep the footer as the protected, `layoutPriority(1)` band and let the transcript be the band that yields/scrolls, so even a single tall run + tall footer can never clip the footer. This is a static, #096-safe change mirroring the existing `ViewThatFits`/`ScrollView` idiom already used by the question footer, and it backstops any future growth source the pruning does not cover.

Auto-scroll fix (this pass — "output doesn't scroll all the way to the bottom"): the OUTER transcript `ScrollView` in `AgentDock.transcript` keys its auto-scroll `.onChange` on `segments.count` alone (`AgentDock.swift:263`). During a live run the transcript holds a single, stable-id `.run` segment, so `segments.count` never changes as log text streams in — the outer scroll fires once (when the segment first appears) and then stays frozen for the rest of the run, leaving the newest output below the fold. The inner `RunLogContents` log auto-follows correctly (it keys on `lines.count`, `PlanDetailView.swift:1839`) but only within its own hard `maxHeight: 360` box (`AgentDock.swift:317`), so anything below that box — a tall streaming run's tail, finished-review follow-up actions, a trailing discuss turn — is never brought into view. The cleanup: make the outer transcript's auto-scroll sensitive to the active run's *content length*, not just the segment count, via a pure, unit-tested key helper (mirroring the existing `RunLogContents.scrollTarget(for:)` idiom) so the `.onChange` re-fires as the active run streams. This is a value-keyed `.onChange` → `scrollTo(id, anchor:.bottom)` change with no size measurement (#096-safe). The nested-scroll `maxHeight: 360` cap is left in place (removing it is a larger finished-run layout change — see Assumptions); keying the outer trigger on content length fixes the reported symptom without that churn.

## Diagnosis

This bug has **two co-primary causes**: run-segment stacking (drives the "clipped after using the plan a while" symptom) and an outer-transcript auto-scroll that freezes during streaming (drives the "doesn't scroll all the way to the bottom" symptom the user reported in this pass). Both are addressed.

**Most likely (A — clipping):** The dock transcript **accumulates a `.run` segment for every action and never prunes finished ones**, so after a few actions on one plan (elaborate → execute → review, interleaved with discuss turns) the stacked run logs exceed the persisted `agentDockHeight` cap and the newest/last line is cropped at the dock's bottom edge — "the agent view appears to be refreshed with every action" is exactly what the user expects but is NOT what happens. (`Sources/Plans/PlanAgent.swift:125` append-only `beginRunSegment`; `Sources/Plans/PlanAgent.swift:152-161` `completeRunSegment` keeps the finished segment; `Sources/Plans/PlanAgent.swift:226-233` `transcriptReset` spares `.run` segments; class doc `Sources/Plans/PlanAgent.swift:15-19` states the accumulate contract; no UI path calls `reset()` at `Sources/Plans/PlanAgent.swift:283-290`)

**Most likely (B — doesn't scroll to bottom):** The OUTER transcript `ScrollView` auto-scrolls on `.onChange(of: segments.count)` (`Sources/Plans/AgentDock.swift:263`), but a live run is a single, stable-id `.run` segment, so `segments.count` is **invariant while log text streams**. The outer scroll fires exactly once (when the segment first appears) and then never re-fires for the rest of the run, so the newest streamed output ends up below the fold — the user's expectation of auto-follow-to-bottom is not met. The inner `RunLogContents` log *does* auto-follow on `lines.count` (`Sources/Plans/PlanDetailView.swift:1839`) but only inside its hard `maxHeight: 360` box (`Sources/Plans/AgentDock.swift:317`), so content below that box is never scrolled into view by the frozen outer container. This is the classic "count change vs. content length" auto-scroll bug, on the outer view. **Confidence:** high.
**Evidence:** Every launch path calls `beginRunSegment` → `transcript.append(.run(run))` (TaskRunner.swift:1720 run, :1738 review, :1839 capture; PlanAgent.swift:125), and nothing removes prior finished runs: `completeRunSegment` only flips `state = .idle` (PlanAgent.swift:160), `transcriptReset` (the "New conversation" path, AgentDock.swift:190 → TaskRunner.swift:2040) filters out only `.turn` cases (PlanAgent.swift:227-230), and `dismissCurrentRun` drops only the single current run (PlanAgent.swift:295-302). `PlanAgentTests` at L88-111 lock this accumulate-and-keep behaviour in as intended. The dock renders the whole list in `ForEach(segments)` (AgentDock.swift:254) and auto-scrolls to `.bottom` on count change (AgentDock.swift:263-266), so the growing tail is pinned against the clipped edge.
**Confidence:** high

**Alternative:** Pure layout starvation — the footer has no reserved height and is the last child under an infinitely-flexible transcript, so a single tall run + tall footer under the `agentDockHeight` cap can clip the footer even with no stacking. (`Sources/Plans/AgentDock.swift:128-133` transcript/footer ordering; `Sources/Plans/AgentDock.swift:628` the `maxHeight` cap; `Sources/Plans/AgentDock.swift:631` the `.layoutPriority(1)`) — **Confidence:** medium. This is a real secondary hazard and is addressed by the retained defensive layout fix, but it is not the "sometimes, after using the plan a while" mechanism the screenshot and the user's report describe.

**Alternative:** The global, persisted `@AppStorage("agentDockHeight")` lets a small height set on one plan apply to a taller transcript on another — a "sometimes" amplifier of both the stacking and the layout mechanisms, not itself the cause. (`Sources/Plans/AgentDock.swift:607-608`, `Sources/Plans/AgentDock.swift:116-119`) — **Confidence:** low

**Alternative (nested scroll, re: cause B):** The inner `RunLogContents` hard `maxHeight: 360` + its own `ScrollView` (`Sources/Plans/AgentDock.swift:317`, `Sources/Plans/PlanDetailView.swift:1805`) makes the run log an independently-clipping sub-scroller: even if the outer trigger were fixed, a run log taller than 360pt scrolls *inside its box* while content below the box (finished-review actions, a trailing turn) still needs the outer scroll to move. — **Confidence:** medium. Contributes to "doesn't scroll all the way down" but is secondary to cause B; removing the cap is a larger finished-run layout change, so this pass fixes the outer trigger and leaves the cap in place (see Assumptions).

**Alternative:** ~~The run segment's inner `RunLogContents` fixed `maxHeight: 360` + bottom padding crops the log's last line (as a CLIPPING cause).~~ — disproved **as a clipping cause**: a single over-long log scrolls inside the transcript rather than clipping at the dock edge, so it is not the reported clipping band. (Note: the same `maxHeight: 360` IS a real *scroll-reach* contributor — see the nested-scroll alternative above — but that is a distinct symptom. Kept for the record.)

**To confirm:**
- Cause A (clipping): on a single plan, run two or more distinct actions (e.g. Refine/Elaborate then Execute). If **multiple stacked run segments** (two collapsible run headers) are visible in the dock, the stacking hypothesis is confirmed. Segment count after the second action discriminates cleanly.
- Cause B (doesn't scroll to bottom): start one run whose streaming output is taller than the visible transcript and **watch whether the OUTER scroll offset ever moves after the first chunk** — it will not. Equivalently, place a segment or finished-review actions AFTER a short (<360pt) run and stream text: if the outer view fails to follow to the bottom while the inner log is fully visible, the `segments.count`-bound outer trigger (cause B) is confirmed as the driver.
