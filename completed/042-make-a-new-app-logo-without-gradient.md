## What
Make a new app logo without the gradient background. Flatter and more modern.

The current app icon is generated by `Tools/make-icon.swift`: it draws an 80%-inset
squircle tile filled with a diagonal blue→purple→pink gradient and a centered white
`list.bullet` SF Symbol glyph, exports a 10-size `.iconset`, which is converted to
`Resources/Plans.icns` via `iconutil`. `build.sh` / `install.sh` copy the committed
`.icns` into the app bundle. This task replaces the gradient with a flat, single-color
modern design.

## Why
Adds value by giving the app a cleaner, more modern visual identity. A flat,
single-color icon (no gradient) reads more crisply at small sizes, feels current
alongside modern macOS apps, and is simpler to maintain.

## How
- [x] Step 1: In `Tools/make-icon.swift`, remove the `gradientColors` array and the
      diagonal `NSGradient.draw(in:angle:)` call; replace the tile fill with a single
      flat brand color (modern indigo `srgb 0.357, 0.420, 0.941` ≈ `#5B6BF0`) applied
      via `NSColor.setFill()` + `tileRect.fill()`. Keep the squircle (80% inset,
      0.2237 corner radius) and the centered white `list.bullet` glyph.
- [x] Step 2: Add an XCTest (`Tests/PlansTests/MakeIconTests.swift`) that compiles the
      icon-drawing logic and asserts the rendered tile is a flat single-color fill
      (gradient-free) — e.g. render a small PNG and verify the tile-interior pixels are
      uniform (within tolerance) rather than varying across the diagonal, and that a
      gradient is not used. Follow the project's per-test temp-dir fixture convention.
      (Red → Green: write the assertion first, then make `make-icon.swift` satisfy it.)
- [x] Step 3: Regenerate the icon artifact: run `swift Tools/make-icon.swift` to emit
      `Plans.iconset/`, convert with `iconutil -c icns Plans.iconset -o Resources/Plans.icns`,
      then remove the temporary `Plans.iconset/` directory. Commit the new `Plans.icns`.
- [x] 👁 Step 4: Build and launch the app (`./build.sh`) and confirm the new flat logo
      renders correctly in the Dock / Finder / Cmd-Tab at multiple sizes and reads well
      on both light and dark backgrounds. (Observation — deferred to review in worktree/yolo mode.)

## Assumptions

### Initial (from elaboration)
- [low] Chose a flat modern indigo (`#5B6BF0`) as the single background color. **Why:** Task says "flatter and more modern" but specifies no color; indigo reads well on both light and dark Docks, is distinct from the muted dark gradient, and feels contemporary. Easily tunable if the user prefers another hue.
- [high] Kept the `list.bullet` glyph (white) rather than switching symbols. **Why:** It is the established brand mark, shared with the menu-bar icon (`MenuBarLabel.swift`), so retaining it preserves visual continuity; the task asked to change the background, not the mark.
- [high] Kept the existing squircle geometry (80% inset, 0.2237 corner radius). **Why:** These match native macOS Big Sur+ icon conventions and were deliberately chosen in task #013; "more modern" is achieved via the flat fill, not by altering the well-formed tile shape.
- [low] Left `MenuBarLabel.swift` unchanged. **Why:** Task scope is the app icon; the menu-bar glyph already renders flat (no gradient) so it is already consistent with the new direction. Syncing further would be a separate task.
- [low] Added a lightweight render test guarding the no-gradient requirement. **Why:** The repo follows TDD and a test suite exists; a flat-fill regression test protects the core requirement without over-engineering an icon-diffing harness.

### Discovered during execution
- [high] Solved the make-icon.swift ↔ library sharing problem by EXTRACTING the canonical drawing logic into `Sources/Plans/IconRenderer.swift` (an `enum IconRenderer` with `static let brandColor`, `static func drawIcon(pixelSize:)`, `static func renderPNG(pixelSize:)`). The test imports `Plans` and exercises `IconRenderer` directly. **Why:** `make-icon.swift` is a standalone script run via `swift Tools/make-icon.swift` and is NOT linked against the `Plans` library target, so it cannot `import Plans`; testing the script via process-spawn would be fragile. The enum is the single source of truth the test guards.
- [low] `Tools/make-icon.swift` still contains its OWN copy of the drawing logic (now flat-fill) because, as a standalone script, it cannot import the library. This is acceptable duplication per the plan's fallback; I added a header comment in make-icon.swift noting it MIRRORS IconRenderer and MUST stay in sync, and the canonical `brandColor` constant matches exactly. **Why:** No feasible way for a `swift Tools/...` script to link the SwiftPM library without restructuring the package into a multi-target executable, which is out of scope.
- [low] Final brand color kept exactly as specified: `NSColor(srgbRed: 0.357, green: 0.420, blue: 0.941, alpha: 1.0)` (≈ #5B6BF0). Not adjusted.
- [high] Pixel-sampling strategy: render a 128px PNG, decode with `NSBitmapImageRep(data:)`, sample a 4x4 cluster at canvas fractions 0.18–0.30 in both axes (inside the squircle interior, clear of the central glyph and the ~0.10 transparent margin). Assert all sampled pixels match each other within accuracy 0.012 per RGBA channel (proves uniform/flat, not gradient) and alpha == 1.0.
- [high] Brand-color assertion compares the sampled tile color against a brand REFERENCE rendered through the SAME NSBitmapImageRep deviceRGB→PNG→decode pipeline (helper `renderedBrandReference`), within accuracy 0.03. **Why:** Sampling a decoded PNG returns pixels in the bitmap's deviceRGB space; comparing directly against the raw sRGB brand NSColor disagreed by ~0.07/channel on this display profile (observed 0.43 vs 0.357). Pipeline-to-pipeline comparison asserts brand identity robustly without baking in a display-specific color-space shift.
- [low] Regenerated `Resources/Plans.icns` is 97KB vs the prior ~761KB gradient version — the flat fill compresses far better. Confirmed non-empty and newer than the previous artifact.

## Changes
- `Tools/make-icon.swift`: Removed the 3-stop `gradientColors` array, the diagonal
  `NSGradient.draw(in:angle:)` call, and its fallback branch. Tile is now filled with a
  single flat brand indigo (`NSColor(srgbRed: 0.357, green: 0.420, blue: 0.941, alpha: 1)`,
  ≈ #5B6BF0) via `setFill()` + `tileRect.fill()`. Squircle geometry (80% inset, 0.2237
  corner radius) and the centered white `list.bullet` glyph are unchanged. Header comment
  updated; marked as a mirror of `IconRenderer`.
- `Sources/Plans/IconRenderer.swift` (new): Canonical, testable icon-drawing logic extracted
  into the `Plans` library target — `enum IconRenderer` exposing `brandColor`,
  `drawIcon(pixelSize:)`, and `renderPNG(pixelSize:)`. Single source of truth the test guards.
- `Tests/PlansTests/MakeIconTests.swift` (new): Renders a 128px PNG via `IconRenderer`, samples
  a 4×4 interior cluster (clear of glyph and margin), and asserts the background is a uniform
  flat color (no gradient) matching the brand indigo within tolerance. `swift test --filter
  MakeIconTests` passes.
- `Resources/Plans.icns`: Regenerated from the new flat design (now ~97KB vs prior ~761KB
  gradient version).

## Notes
The icon pipeline is a standalone AppKit script (`Tools/make-icon.swift`), so it is not
part of the `Plans` library target. The test in Step 2 must either replicate the small
amount of drawing logic under test or factor a shared, testable drawing function — keep
the test focused on the flat-fill property rather than exact pixel values.
